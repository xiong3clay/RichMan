一、A 激活后的跨重启补偿（N1 残留）
------------------------------------
1.1 改了什么
- storage/types.ts：新增 ActivationUndo（schemaVersion/roomCode/expectedVersion/beforeGame/
  noHumanSinceMs/pauseStartedAtMs/pauseShifted/writtenAtMs）与 RoomStore.writeActivationUndo /
  deleteActivationUndo 可选方法。
- storage/atomic.ts：AtomicOptions 增加 backup?: boolean（默认 true）；
  writeSnapshotAtomic 只在 backup !== false 时复制 snapshot.bak.json。
  这样 activation-undo.json 的原子写不会污染唯一好备份。
- storage/file-store.ts：
  writeActivationUndo（约 222-230）写 rooms/<code>/activation-undo.json；
  deleteActivationUndo（约 231-233）删除；
  applyActivationUndo（约 234-288）在 loadAll 校验快照后执行：
  · snapshot.game.version === expectedVersion → 用 beforeGame 恢复、paused=true、
    真人 online=false、写回 snapshot.json、删 undo、warn 一次；
  · 版本不等（后续合法推进/激活没落盘）→ 只删 undo；
  · undo JSON/字段损坏 → 保留房间、paused=true、warn，不删 undo、不删档；
  · 回滚写盘失败 → 保留 undo 与暂停，下次启动重试。
  loadAll 调用点约 486：`s = await this.applyActivationUndo(code, s)`。
- rooms/manager.ts：writeActivationUndo / deleteActivationUndo 包装（约 417-428）；
  无持久化 store 时 no-op；删除失败只告警。
- ws.ts 最终激活（约 347-372）：在 manager.transact 之前写 undo，
  expectedVersion = result?.state.version ?? 当前 game.version；
  transact 成功（含 online 确认）后在同一房间队列内删除 undo。
  写 undo 失败会抛错，走原有 rollbackConnectionActivation，房间保持暂停。

1.2 测试（apps/server/tests/activation-undo.test.ts，真实临时目录 + FileRoomStore）
- 「激活已落盘、补偿未执行：loadAll 回到 beforeGame 且 paused=true」
  （内存与磁盘 snapshot.json 都回到 version 0，undo 被删除）
- 「stale undo（版本已推进）只删记录，不改游戏」
- 「正常激活清理后 undo 不存在」（manager.writeActivationUndo→deleteActivationUndo→loadAll）
- 「undo 损坏：保留房间并暂停，不删档」（坏 JSON 仍在，房间仍能加载）
另外 pause-archive-atomic.test.ts 的 16 条真实 WS 重连用例全部通过，
说明正常激活路径会写并清理 undo，没有破坏既有老化/平移语义。

二、B 归档隐藏残留目录清理（N7 边界）
--------------------------------------
2.1 改了什么
- storage/archive-policy.ts：新增 ARCHIVE_RESIDUE_TTL_MS = 60 * 60_000。
- storage/file-store.ts pruneArchives（约 412-438）：每次 cleanupArchives 先扫描
  archive/ 与 rooms/ 的直接子目录，匹配 `.archived-source-*`、`.staging-*`、`.restore-*`
  且 mtime 超过 1 小时的递归删除；删除失败写入 failed 并 warn，不抛异常；
  1 小时内的保留，避免误删进行中的归档/恢复。
2.2 测试（apps/server/tests/archive-residue.test.ts）
- 「archive/rooms 下三类残留超过 1 小时才清理，1 分钟内的保留」：
  三个真实目录 utimes 到 2 小时前 → 消失并进入 removed；
  新建的 `.staging-new` 保留。

三、C 坏归档隔离（N7 边界）
----------------------------
3.1 改了什么
- storage/archive-policy.ts：ARCHIVE_QUARANTINE_FAILURES = 3。
- storage/file-store.ts：新增 archiveFailures Map（按归档目录计连续失败）；
  pruneArchives 读取失败时 +1，成功后清零；达到 3 次时把目录 rename 到
  archive/.quarantine/<原名>/（重名追加时间戳），结果记录在
  ArchiveCleanupResult.quarantined，warn 写出隔离路径；隔离成功当次不再进 failed。
  隔离区文件保留；容量统计把 .quarantine 下文件大小计入 bytes，
  但 quarantined 不进入 FIFO 删除列表。
- ArchiveCleanupResult 增加 quarantined: string[]（结果字段扩展，原字段不变）。
3.2 测试（apps/server/tests/archive-residue.test.ts）
- 「连续 3 次 cleanupArchives 后进入 .quarantine，随后不再 failed」：
  第 1/2 次 failed 含坏档；第 3 次 quarantined 含目标且 failed 不含源目录；
  第 4 次 failed/quarantined 都不再出现，隔离目录仍在。
