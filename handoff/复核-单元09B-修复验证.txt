十一、E1–E4 判断
E1 status 在 stale 状态 + 同端口健康 RichMan 时直接 ok=false
  判定：YES，属于诊断失真，应该修复（should-fix）。
  证据：18886 /health 返回 200 service=richman；另一 dataDir 写 stale 状态
  （pid=999999，port=18886）；status -Json -DataDir staleDir 输出：
    {"ok":false,"port":18886,...,"server":{"ok":false,...,"reason":"状态文件记录的进程已退出"}}
    exit 1
  原因：status.ps1:39-45 在 state 非 running 时直接写 reason，只有 else 分支才探测
  /health（status.ps1:46-63）。stale/mismatch 不等于服务一定不健康。
  建议：state 非 running 时仍探测生效端口 /health；若返回 RichMan 健康，可报
  server.ok=true 并附 “状态文件过期” 警告；或至少增加 healthOk 字段，避免诊断失真。
  严重度：should-fix（只读诊断；不影响 stop 安全）。

E2 旧版 startedAtUtc 是健康检查后的 UtcNow，新 stop 可能判 mismatch
  判定：YES，需要文档标注迁移方式（should-fix，文档）。
  证据：无关 node 实际 StartTime 14:46:28，旧式 state 写 14:46:32（差 4 秒）：
    stop exit 2，WARN“相差 4 秒，pid 可能已被复用”，state 保留，dummy 仍活。
    改成真实 StartTime 后 stop exit 0 并杀掉。
  旧 start-lan 在健康检查之后才取 UtcNow；旧 tunnel 更是在 URL 捕获后才取时间，
  差值可能 >2 秒。升级时旧实例仍在运行，新 stop 会安全地拒绝停止并 exit 2。
  建议：在 注意事项/运行与验收 写明迁移步骤：升级前用旧脚本 stop；
  或人工确认后手动停止旧进程并删除旧 server.json/tunnel.json；
  不要为了迁移放宽 ±2 秒或退回只看 pid+名称。
  严重度：should-fix（安全行为正确，缺运维说明）。

E3 管道捕获脚本输出时子进程句柄继承
  判定：真实控制台/文件重定向不受影响；CI 管道需要更强约定（nit）。
  证据：同一 start-lan（18885）文件重定向耗时 4 秒返回；
  用隐藏 PowerShell 控制台启动 start-lan（18887）3.5 秒返回 exit 0；
  但用 `... start-lan.ps1 | ...` 仍会等 node 子进程退出。
  文档 注意事项 §5、运行与验收 §六已如实写；不建议为此改生产脚本。
  建议：README/运行验收明确“CI 必须重定向到文件或 Start-Process 包装”，
  不要让测试把常驻服务输出直接接管道。严重度：nit。

E4 stop “幂等”承诺 vs mismatch exit 2、状态保留
  判定：文档自相矛盾，必须修文档（must-fix 文档）。
  现状代码：无状态文件 → “未在运行” exit 0（幂等）；mismatch/unknown/坏 JSON →
  exit 2、状态保留、不杀；stale → 清状态 exit 0。这个行为是正确的、可重复的
  （重复 mismatch 仍是 exit 2、状态不动），但“幂等 = 成功/exit 0”的旧表述不准确。
  矛盾位置：
    成果报告:43 “不匹配/已退出只清理状态并 WARN”（旧行为）；
    注意事项:25-26 “PID 复用时进程名不匹配就只 WARN 并清理状态”（旧行为）；
    下一阶段:19/53 “只按 pid + 进程名白名单停止”（漏了真实启动时间）；
    README:45 “可重复执行（幂等）”与 exit 2 并列，容易被理解为总是成功。
  建议：明确写成“无状态文件幂等 exit 0；mismatch/unknown/坏 JSON 是人工确认态，
  exit 2 且不删状态；stale 才清状态”。严重度：must-fix（文档）。
