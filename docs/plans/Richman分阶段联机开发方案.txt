版本：V1.1（已按坦克大战“自建服务器”模式修订）
依据文件：大富翁.cpp
联机参考项目：D:\Lianjunjie\Cqianyi\文档\deepseek-harness\default-workspace\tank-battle-git
目标：在现有规则基础上，逐步做成可由 Windows 电脑开服、电脑和手机共同加入的成熟联机游戏。

============================================================
一、先明确项目边界和联机理解
============================================================

1. 当前代码的本质
当前版本不是传统“走地图、买地产”的大富翁，而是 2～10 人参与的回合制金融生存游戏，核心为：
- 初始 100 金币，最后一名未破产玩家获胜。
- 每轮依次结算利息、银行逾期、玩家行动、共同赌博、每三轮纳税。
- 玩家可向银行或其他玩家借款、还款、催债。
- 信用、债务、放贷、危险自救和破产构成主要策略。

第一阶段开发不要额外加入地图、地产、道具、排行榜、账号体系等新玩法，先把现有规则做正确、联机做稳定、界面做清楚。

2. 已核实的“坦克大战第三种联机方式”
第三种方式在坦克大战界面中叫“自建服务器”，不是 P2P：
- 你的电脑运行 Node.js，同一个进程提供静态网页、/health 健康检查、/ws WebSocket 和房间管理。
- 局域网设备访问 http://你的内网IP:8000/，使用 4～8 位数字房间号开房或加入。
- 公网通过 cloudflared 建立 Cloudflare 临时隧道，玩家访问 https://xxx.trycloudflare.com；HTTPS 页面自动使用 WSS，地址每次启动可能变化。
- 页面由自建服务器提供时，客户端从 location.origin 自动得到服务器地址，不要求玩家另外填写 WebSocket 地址。
- 服务器注入座位号并管理 join / ready / room / start / peer-left / error 等房间消息。

坦克大战与 Richman 的关键差异：
坦克大战的 Node 服务器只做消息中继，开房间的浏览器负责移动、碰撞、生命和胜负。Richman 只复用它的“自建服务器连接方式、同源页面、房间骨架和启动体验”，不能照搬浏览器权威；Richman 的 Node 服务器必须直接执行财务规则，否则房主可以修改金币、债务和赌博结果。

参考位置：
- tank-battle-git\server\relay.js：端口 8000、监听 0.0.0.0、/health、/ws、房间与座位。
- tank-battle-git\net.js:506-656：自建服务器地址转换、4～8 位房间号和 WebSocket 协议。
- tank-battle-git\server\start-lan.bat：局域网启动。
- tank-battle-git\server\start-tunnel.bat：cloudflared 临时公网隧道。
- tank-battle-git\README.md:92-121：实际使用与启动说明。

3. Richman 最终使用方式
- 你的电脑启动 Richman 自建服务器，默认端口与坦克大战保持一致，使用 8000，可用 PORT 修改。
- 你的电脑通过 http://localhost:8000 进入游戏。
- 同一局域网的其他设备通过 http://你的局域网IP:8000 进入。
- 页面显示局域网地址和手机扫码入口，玩家用 4～8 位数字房间码及昵称加入，房间容量为 2～10 人。
- 不在同一网络时，通过 Cloudflare 临时 HTTPS/WSS 隧道访问同一个服务器，不要求每个玩家安装 Node 或 cloudflared。
- 电脑端和手机端均使用浏览器；后续可增加 PWA“添加到主屏幕”，首版不开发原生 App。
- 服务器电脑必须保持开机且不能睡眠；关闭服务窗口即停止联机，存档恢复不能代替进程持续运行。

============================================================
二、必须采用的技术架构
============================================================

1. 总体原则：服务器权威
所有金币、债务、利息、随机结果、回合推进和胜负都只由服务器计算。
客户端只能提交“我想做什么”，不能提交“我的金币现在是多少”或“随机结果是什么”。
服务器校验通过后再更新状态，并向各客户端发送该玩家有权看到的状态。

这样做可以避免：
- 多设备状态不一致。
- 重复点击导致重复转账或重复计息。
- 修改浏览器数据作弊。
- 某一玩家断线后整局无法恢复。

2. 推荐技术栈
采用一套 TypeScript，降低 DeepSeek、Trae、Qorder 多轮开发时的上下文成本：
- 前端：React + Vite + TypeScript，响应式 Web 页面。
- 实时通信：浏览器原生 WebSocket + JSON 文本消息，自建 /ws 通道，自行实现带会话令牌的重连和心跳。
- 服务端：Node.js LTS + 同源 HTTP 静态服务 + ws 库；复用坦克大战的部署形态，但不复制其手写 WebSocket 帧编解码。
- 规则校验：Zod，前后端共享协议和基础数据结构。
- 音频：Howler.js，音频文件随客户端本地加载，不由服务器持续推流。
- 数据存储：SQLite，保存房间快照、玩家连接信息和事件记录。
- 测试：Vitest（规则及接口）+ Playwright（多页面联机验收）。
- 包管理：pnpm workspaces。

3. 推荐目录
apps/web：电脑/手机浏览器客户端。
apps/server：房间、通信、校验、存档和静态页面服务。
packages/game-core：纯规则引擎，不依赖浏览器、网络、数据库。
packages/shared：共享类型、协议、错误码、规则常量。
tests：跨端集成测试和端到端测试。
assets/audio：有合法使用授权的音乐和音效。
handoff：每阶段成果、测试、交接及注意事项 txt。
scripts：安装、启动、测试、备份脚本。

4. 网络与状态同步
- 服务端同时提供客户端静态页面、/health 和 /ws，首版只开放 8000 一个服务端口，监听 0.0.0.0。
- 只公开 apps/web/dist 等专用公开目录，不能像坦克大战开发版一样把整个仓库作为静态根目录，避免源码、存档和配置被下载。
- 客户端默认从 location.origin 派生连接地址：http→ws、https→wss，并自动补 /ws；也可手动填写服务器地址。
- 房间控制消息参考坦克大战：join / ready / room / start / peer-left / error；业务动作和状态消息单独分类。
- 座位、容量、角色和发送者均由服务器分配或注入，不能信任客户端自行声明。
- 每次操作带 commandId 和 expectedVersion；服务器去重并检查版本。
- 每次状态变化增加 version。
- Richman 是回合制游戏，不照搬坦克大战输入 30Hz、快照 20Hz；采用“动作命令 + 状态版本 + 事件推送”。
- 2～10 人房间的数据量很小，首版直接发送“按玩家权限过滤后的完整快照”，比复杂增量同步更可靠。
- 请求失败要明确提示，不允许前端先扣钱再等待服务器确认。
- 生产随机结果由服务器生成；测试环境允许注入固定随机序列。

5. 基本通信内容
客户端命令示例：创建/加入房间、准备、开始、银行借款、发起私人借款、同意/拒绝借款、还款、催债、提交赌注、逾期还款选择、危险自救、结束行动。
服务器消息示例：加入结果、房间快照、阶段变化、操作结果、待处理借款请求、错误提示、玩家重连、游戏结束。
另提供 /health 健康检查，返回 ok、服务标识、版本、在线连接数和房间数，便于 Harness 与启动脚本判断服务器是否真正启动；房间详细状态不对未加入者公开。

三、开发前必须冻结的规则（推荐默认值）
============================================================

以下默认值已修正源代码中会影响成熟联机版的冲突。第 0 阶段把它们写入 handoff/规则决策表.txt；之后 AI 不得擅自改动，改动必须先记录原因和影响的测试。

1. 回合与金额
- “回合”指一整轮，不是某个玩家的一次行动。
- 人数为 2～10 人，座位号稳定，玩家显示名不作为身份主键。
- 所有金额在程序内部使用“整数分”，界面再显示为元/金币，禁止使用 float 直接记账。
- 利率使用基点保存，例如 10% = 1000 基点。
- 每笔贷款每轮分别计息，四舍五入到分；同一笔贷款同一轮只能计息一次。

2. 每轮流程
阶段 1：所有有效贷款结算一次利息。
阶段 2：处理到期银行贷款。
阶段 3：财务信息更新，不设置需要逐人点击确认的阻塞步骤。
阶段 4：按座位顺序，每名存活玩家执行一次主要行动；查看规则、财务和债务不消耗行动。
阶段 5：所有存活玩家同时私下提交赌注、猜测和杠杆选择；全部锁定后公布同一个服务器随机结果。
阶段 6：仅在轮数能被 3 整除时，依次收税并处理危险自救。
最后检查是否仅剩一名存活玩家。

3. 银行贷款
- 信用良好且没有未结清或失信银行贷款时，可申请普通银行贷款。
- 普通银行贷款上限为申请时金币的 50%，金额必须大于 0。
- 私人负债是否影响普通银行贷款作为可配置规则；首版默认不影响，但界面必须如实说明。
- 每轮利息 10%，第 N 轮产生的贷款在第 N+1 轮开始计息，第 N+3 轮利息结算后到期。
- 到期时只能选择“全额还款”或“拒绝还款”；余额不足即使选择还款也会失信。
- 主动还款可部分或全额偿还，还款金额必须大于 0 且不能超过剩余债务。

4. 失信后的银行债务（对源代码的必要修正）
源代码在失信时将借条失效、欠款清零，会丢失需要展示的金额，新版本不得照搬。
推荐规则：
- 失信不免除债务，贷款状态改为 DEFAULTED。
- defaultedBankDebtCents 永久保留本局失信时未偿还的银行本息，其他玩家可以看到该金额。
- 失信后停止该笔贷款继续复利，避免欠款无限增长。
- 失信玩家本局不能新增普通银行贷款，也不能使用赌博杠杆。
- 失信后仍可查看和偿还历史欠款；还清不自动恢复本局信用。
- 总债务仍包含失信欠款，不能因为状态变化而从账上消失。

5. 私人借款（对源代码的必要修正）
- 借款人发起请求：选择出借人、本金、每轮利率（0～100%）。
- 出借人必须明确同意才转账；拒绝、超时或取消均不产生债务。
- 借款人提交请求即消耗本次主要行动，防止无成本反复骚扰；出借人同意/拒绝不消耗自己的行动。
- 同意时再次检查出借人余额，转账和生成借条必须是一个原子操作。
- 借款请求必须给出借人展示：借款人昵称、信用状态、借款金额、利率、借款人的银行失信欠款、私人负债总额、与自己相关的历史债务。
- 出借人不能借出超过自己当前余额的金额，不能自己借给自己。
- 满一整轮后，出借人可以催债；单次催收不能超过剩余本息，也不能超过借款人当前金币。
- 部分催债只减少本次实际转账金额，必须修正源代码中按原总债务扣账的问题。
- 借款人可主动部分或全额还款，双方余额、债务和应收款必须同步更新。

6. 赌博
- 使用游戏金币，不接入任何真实支付。
- 每轮所有存活玩家可下注 0 到当前金币，猜测 0 或 1。
- 未使用杠杆：猜对净增下注额，猜错净减下注额。
- 双倍杠杆：仅信用良好者可用；猜对净增两倍下注额，猜错净减两倍下注额。
- 其他玩家的猜测和杠杆在全部锁定前不得公开。
- 超时未提交默认下注 0，避免整局无限等待。
- 输后金币小于 0 时，自动生成“赌博透支贷款”，金额为缺口，金币归零；该贷款按银行贷款计息和到期规则处理。
- 赌博透支贷款是特殊贷款，不受普通贷款 50% 上限限制，并与普通贷款分开标识。

7. 税收、危险和破产
- 每三轮向每名存活玩家收 20 金币。
- 扣税后金币小于 0，进入危险状态，可尝试向玩家借款、催债自救或放弃。
- 危险状态必须有倒计时；超时按放弃处理，防止玩家长时间卡住全房间。
- 自救结束后仍小于 0 则破产，破产玩家不能继续行动。
- 破产时停止其所有贷款继续计息；私人未收债务记为 BAD_DEBT，银行未还债务记为失信欠款，历史记录保留供查询。
- 最后一名存活玩家获胜；全员破产则无人获胜。

8. 等待与超时
建议默认值，写入房间配置而不是散落在代码中：
- 普通行动 60 秒，超时视为结束行动。
- 私人借款请求 45 秒，超时视为拒绝。
- 银行到期选择 45 秒，超时视为拒绝还款。
- 赌博提交 45 秒，超时视为不下注。
- 危险自救 60 秒，超时视为放弃。
计时以服务器时间为准，客户端只显示倒计时。

四、玩家信息和界面要求
============================================================

1. 自己的信息必须始终容易找到
桌面端设置固定“我的财务”面板，手机端放在底部导航第一项，包含：
- 当前金币、总负债、总应收、信用状态、存活/危险状态。
- 普通银行贷款、赌博透支贷款、失信欠款分别显示。
- 每笔银行贷款：本金、当前剩余本息、利率、借款轮、到期轮、状态。
- 每笔私人债务：对方、当前剩余本息、利率、借款轮、是否可催债/应还款。
- 当前轮数、阶段、自己是否已行动、剩余操作时间。
- 本轮利息、税收、赌博输赢和转账的事件记录。

2. 其他玩家的信息
玩家列表默认显示：昵称、座位、存活状态、信用状态、当前是否危险/离线。
信用用“图标 + 文字 + 颜色”共同表达，不能只靠红绿颜色。
失信玩家显示“失信，欠银行 X 金币”，金额来自 defaultedBankDebtCents 汇总。
不默认公开其他玩家全部金币和每笔私人合同，避免泄露不必要的策略信息。

3. 债务查询中心
任何阶段都可打开，不消耗行动，包含：
- 与我相关：我借入、我借出、待我确认、已完成、坏账。
- 公共信用：各玩家信用状态和失信银行欠款。
- 支持按借款人、出借人、状态、轮数筛选。
- 与我相关的合同显示完整明细；与己无关的私人合同仅显示规则允许的公共摘要。
- “别人向我借钱”单独作为高优先级通知和待办角标，打开后直接看到风险信息及同意/拒绝按钮。
- 所有金额变化后，查询中心与主面板必须由同一份服务器状态更新，不能各算各的。

4. 响应式布局
桌面端：顶部房间/轮次/音频，中间当前阶段与操作区，左侧玩家列表，右侧我的财务和事件。
手机端：顶部精简状态，中部当前操作，底部“我的、玩家、债务、记录”四个入口。
所有主要按钮适合触控，关键操作二次确认，错误提示说明原因和解决办法。
网络断开、重连中、服务器已关闭必须有明显状态，不得让玩家误以为操作成功。

5. 简短新手教程
首次进入显示 5 页以内、约 60 秒可读完的图文教程：
- 目标与一轮流程。
- 银行借款、到期和失信后果。
- 私人借款需要对方同意，以及如何催债/还款。
- 赌博、杠杆、每三轮纳税与危险自救。
- 我的财务和债务查询入口。
每页都有“跳过教程”，结束后可跳过；页面提供“重新查看教程”。
用 localStorage 记录是否看过，但换设备仍可选择查看，不依赖教程状态才能正常游戏。

五、配乐和音效方案
============================================================

- 大厅、正常回合、危险状态、结算分别配置可循环 BGM；危险音乐切换要平滑，不能频繁重启。
- 借款请求、转账成功、到期警告、破产、胜利配置短音效。
- 提供总静音、音乐音量、音效音量，并保存到本机。
- 浏览器禁止自动播放时，在玩家第一次点击“进入游戏/开启声音”后再播放，不能反复弹错误。
- 手机切后台、锁屏、断线重连后，音频不得多重叠加播放。
- 首版只使用自制、明确授权或许可兼容的音频，保留素材来源和许可证清单。
- 音频加载失败不阻塞游戏逻辑。

============================================================
六、分阶段实施计划（必须逐阶段验收）
============================================================

第 0 阶段：规则冻结与工程骨架
目标：消除歧义，建立后续 AI 可重复进入的工程。
工作：
- 将第三部分写成 handoff/规则决策表.txt，逐条标明“源代码行为/新行为/原因”。
- 建立上述 monorepo、TypeScript、共享类型、测试和格式化配置。
- 定义房间、玩家、银行贷款、私人贷款、借款请求、赌注、事件等数据模型。
- 定义阶段状态机、错误码和命令协议初稿。
- 建立 Git，忽略依赖、构建产物、存档和密钥。
验收：
- 新环境按文档可安装并启动空前端、空服务器。
- health 接口可访问，基础测试和构建命令真实通过。
- 规则决策表没有“以后再定”的核心财务问题。
禁止：本阶段不实现完整 UI，不提前堆玩法。

第 1 阶段：纯规则引擎
目标：不依赖网络和界面，用测试证明规则正确。
工作：
- 在 packages/game-core 实现完整回合状态机。
- 实现银行/私人借贷、同意拒绝、还款、催债、利息、失信、赌博、税收、自救、破产和胜负。
- 所有余额、总债务、总应收由账本计算或严格校验，不允许多处独立修改造成漂移。
- 使用可注入随机数，编写正常、边界和回归测试。
必须覆盖：
- 同轮不重复计息，跨轮只计一次，金额四舍五入。
- 到期还款、拒绝、余额不足和失信欠款保留。
- 私人借款未经同意不转账；同意时余额不足不生成借条。
- 部分还款、部分催债、全额结清后双方账目一致。
- 赌博杠杆、透支贷款、税收自救、破产和最后一人获胜。
- 重复 commandId 不会重复扣款或推进阶段。
验收：规则测试全部通过；能用测试脚本完整模拟至少一局，不依赖人工控制台输入。
禁止：为赶进度把规则重新写进 React 组件或 Socket 回调。

第 2 阶段：自建服务器局域网最小可玩联机版
目标：按坦克大战第三种方式，尽早验证“你的电脑开服、别的设备加入”的关键路径。
工作：
- 建立同源 HTTP + /health + /ws 服务，默认 8000 端口，提供启动后打印本机/LAN 地址的脚本。
- 实现创建房间、4～8 位数字房间码、2～10 人容量、昵称加入、服务器分配座位、准备、房主开始。
- 实现 join / ready / room / start / peer-left / error 房间消息；开房者管理房间，但不是规则权威。
- 实现 Node 服务器权威调用第 1 阶段规则引擎，不能只做消息中继。
- 实现最小大厅和 game 页面、状态快照、错误提示、操作锁和倒计时。
- 页面由服务器提供时自动检测 /health 并使用 location.origin；服务器显示本机地址、局域网地址及手机二维码。
- 先打通两名真实浏览器玩家完成一整轮，再扩展到 10 人。
验收：
- 电脑 A 开服，电脑 B 和手机 C 通过 http://A的内网IP:8000 加入，无需分别安装依赖。
- 三个客户端看到的轮数、阶段、座位和公共状态一致。
- 非当前玩家不能代替当前玩家行动，刷新页面不会重复执行操作。
- 伪造 role、seat、from 或 cap 不能越权，服务器日志能定位每次命令、拒绝原因和状态版本。
禁止：此阶段不追求美术，不允许客户端或房主浏览器自行计算金币。

第 3 阶段：完整联机交互与债务中心
目标：把所有规则变成真正可用的多人交互，而不是单机按钮拼接。
工作：
- 完成银行借款/还款、私人借款请求和通知、同意/拒绝、催债。
- 完成赌博私密提交、统一开奖、逾期选择、危险自救和阶段超时。
- 完成我的财务、其他玩家信用、失信银行欠款、与我相关债务查询。
- 完成操作历史、待办角标、空状态和错误原因。
- 对并发场景加测试：同时请求同一出借人、出借人余额变化、请求超时、催债与还款竞争。
验收：
- 借款人不能未经出借人同意获得资金。
- 出借人收到请求时可看到规定的风险信息并查询双方历史债务。
- 所有客户端的公开信用和失信欠款一致，双方账本一致。
- 两人和十人房间均可从开局玩到结算，没有永久卡在某一阶段的情况。

第 4 阶段：新手教程、手机适配和音频
目标：形成对普通玩家友好的版本。
工作：
- 实现可跳过、可重看的短教程。
- 完成桌面/手机响应式布局、触控、二次确认、可访问性文字。
- 接入 BGM 和音效、音量设置、浏览器自动播放限制处理。
- 优化阶段反馈：利息、逾期、收税、危险和开奖都有明确动画/提示，但动画不能阻塞服务器结算。
验收：
- 未读源代码的新玩家仅看教程能完成借款、查询债务和还款。
- 常见手机竖屏不横向溢出，主要操作无需精确点小按钮。
- 静音后不再播放；切后台和重连不出现双重音乐。
- 音频关闭或加载失败时，整局仍可完成。

第 5 阶段：断线恢复、存档和安全加固
目标：达到可持续开局的稳定度。
工作：
- 玩家加入时发放随机会话令牌，断线后保留座位；令牌只用于恢复本人，不信任客户端传入的昵称或 playerId。
- WebSocket ping/pong 检测离线，连续超时必须真正关闭失效连接并标记座位离线；不能照搬坦克大战当前只标记 alive 却不关闭的循环。离线不立即破产，按当前阶段倒计时处理。
- 每个被接受的命令完成后保存 SQLite 快照和事件，服务器重启后可恢复房间。
- 数据库写入使用事务；存档带 schemaVersion，升级前备份。
- 校验所有输入，限制昵称长度、命令频率、房间码猜测频率和请求大小。
- 防止重复加入、冒名恢复、越权查看私人合同、伪造他人操作。
验收：
- 玩家刷新、短暂断网、手机锁屏后能恢复本人座位和最新状态。
- 服务器重启后房间可从最近一致状态继续，不重复计息或转账。
- 重复发送同一命令、伪造版本、伪造他人身份均被安全处理。
- 存档损坏有明确报错和备份恢复说明，不静默开新局覆盖旧档。

第 6 阶段：跨网访问、完整测试与发布包
目标：按坦克大战的启动体验，形成别人可按说明运行的 Richman V1.0。
工作：
- 完成 Windows 防火墙、8000 端口、二维码和公网 HTTPS/WSS 隧道配置说明。
- 提供与坦克大战类似的 scripts/start-lan.bat：启动服务并打印 http://内网IP:8000/。
- 提供 scripts/start-tunnel.bat：检查或下载 cloudflared，先启动本地服务器，再执行 cloudflared.exe tunnel --url http://localhost:8000 --no-autoupdate。
- 启动脚本轮询 /health，不能固定等待两秒就假定成功；成功后打印并复制 https://xxx.trycloudflare.com，自动打开本机浏览器。
- 明确提示临时公网地址每次启动可能变化，需要重新分享；V1.0 可使用临时隧道，固定域名和命名隧道属于后续增强。
- 运行期间防止电脑空闲睡眠；关闭窗口时只清理本脚本启动的服务器和隧道，避免误杀其他 Node 进程。
- 公网只暴露游戏公开目录、/health 和 /ws，不暴露数据库、源码、存档和服务器管理端口，不使用路由器 DMZ。
- 完成 Windows 一键启动/停止/备份脚本、依赖安装说明和故障排查。
- 完成单元、集成、Playwright 多端测试及至少一次真人长时间试玩。
- 整理版本号、变更记录、音频授权和第三方依赖许可证。
验收矩阵：
- Windows 本机 + 另一台电脑 + Android 手机 + iPhone（若持有）加入同一局。
- 2 人和 10 人局；普通和失信玩家；断线重连；服务器重启恢复。
- 局域网与 Cloudflare 临时公网隧道各完成至少一局，HTTPS 页面下的 WSS 连接正常。
- 重启隧道后旧地址失效有提示，新地址可重新加入；睡眠防护和关闭清理按说明生效。
- 连续运行多局无重复房间状态、无音频叠加、无明显内存持续增长。
- pnpm test、pnpm build、端到端测试均有真实通过记录。
验收后才标记 V1.0，不得以“代码已生成”代替“已运行验收”。

============================================================
七、DeepSeek Harness 调用 Trae / Qorder 的执行制度
============================================================

1. 角色分工
- DeepSeek Harness：每次只选择一个阶段，分发任务、收集实际测试输出、检查交付文件，不自行假设已经通过。
- Trae：主实现 agent，按阶段范围修改代码并运行测试。
- Qorder：独立复核 agent，检查规则偏差、并发/安全问题、测试缺口，执行复核或修复。
- 如果实际工具能力不同可交换实现与复核角色，但不要让两个 agent 同时无协调地修改同一批文件。

2. 固定工作顺序
读总方案和当前交接 -> 复述本阶段范围 -> 检查环境 -> 实现 -> 测试 -> 独立复核 -> 修复 -> 人工验收 -> 写交接 -> 提交 Git。
上一阶段未通过时，下一阶段只能做阻塞修复，不得继续堆新功能。

3. 每轮给编程 AI 的通用提示词
“请只执行《Richman分阶段联机开发方案.txt》的第 N 阶段。开始前必须阅读本方案、handoff/项目当前状态.txt、上一阶段的成果报告/测试报告/交接说明/注意事项，以及 handoff/规则决策表.txt。先列出你要修改的文件和验收方法，再动手。不得擅自改变已冻结规则，不得把规则逻辑塞进 UI 或网络回调，不得用假数据、注释掉的测试或虚构命令结果冒充完成。完成后运行本阶段要求的测试和构建；无法运行的项目必须标为未验证并写明原因。无论成功或失败，都写齐本阶段四类交接 txt，并更新项目当前状态。发现上一阶段缺陷先记录并修复阻塞项，不要扩大本阶段范围。”

4. 每阶段强制交付的 txt
统一放在 handoff 目录，文件名示例：
- 阶段03-成果报告.txt：完成项、未完成项、主要修改文件、实际测试命令及结果、已知缺陷、Git 提交号。
- 阶段03-运行与验收说明.txt：安装/启动步骤、访问地址、测试账号或房间创建方法、逐步验收操作和预期结果。
- 阶段03-下一阶段交接.txt：当前架构、数据流、协议变化、数据库变化、下一阶段入口文件、必须遵守的约束。
- 阶段03-注意事项.txt：规则歧义、兼容问题、安全事项、临时方案、技术债、绝不能重复出现的错误。
同时更新：handoff/项目当前状态.txt。
该文件只写当前最新有效状态：已完成阶段、当前可运行版本、启动命令、测试状态、阻塞项、下一阶段编号、应阅读的交接文件。

5. 阶段完成定义
只有同时满足以下条件才可报告“完成”：
- 本阶段功能实际运行，不只是生成代码。
- 自动化测试和构建真实执行并保留结果。
- 本阶段人工/多设备验收步骤有记录。
- 没有未说明的阻塞缺陷。
- 四类 txt 和项目当前状态已更新。
- 已做一次可回退的 Git 提交。
否则报告“部分完成/被阻塞”，说明证据和下一步，不允许提前进入新阶段。

============================================================
八、关键测试清单（后续 AI 不得删除）
============================================================

账务不变量：
- 玩家余额变化必须能由已接受的交易解释。
- 总借款 = 所有未结清银行/私人/失信债务之和。
- 总应收 = 作为出借人的有效私人贷款剩余本息之和。
- 同一笔还款不能同时减少两次债务。
- 同一轮重连、刷新、重复消息不能重复计息。

权限与隐私：
- 玩家不能替他人同意、下注、还款或结束行动。
- 未参与某私人合同的玩家不能读取其完整细节。
- 赌博锁定前其他玩家看不到猜测和杠杆。
- 信用和失信银行欠款按公共规则对所有玩家一致。

流程：
- 每个阶段都有完成和超时路径，不存在只能等某个永久离线玩家的死锁。
- 借款、还款、催债同时发生时由服务器串行校验，最终账本一致。
- 游戏结束后拒绝所有经济操作，只允许查看和返回大厅。

体验：
- 教程可跳过也可重看。
- 债务中心随时可查，不消耗行动。
- 别人向我借钱时有明显通知，能直接看到风险信息。
- 失信状态和欠银行金额清晰，不只靠颜色表达。
- 手机端能完成全部操作，音乐可关闭。

============================================================
九、首版明确不做，避免项目失控
============================================================

- 不做真实货币、充值或提现。
- 不做账号注册、排位、好友、聊天、观战和反作弊运营平台。
- 不做主机迁移；你的电脑关闭服务器即无法继续联机，但可从存档恢复。
- 不承诺所有公网环境都能直接端口映射；优先使用受控 HTTPS 隧道。
- 不在 V1.0 前增加地图、地产或新金融体系。
- 不为了画面引入重型 3D 引擎；当前玩法用响应式 UI 和轻量动画更合适。

============================================================
十、建议的实际启动顺序
============================================================

先由 Harness 执行第 0 阶段并让你确认规则决策表，尤其是：
1. 私人负债是否影响银行贷款。
2. 失信欠款停止计息、还清后信用仍不恢复是否接受。
3. 破产后的私人债务记为坏账是否接受。
4. 各阶段倒计时是否合适。
确认后再做规则引擎。不要先写漂亮页面，也不要先接公网；最先证明“账算对”，再证明“多设备能连”，最后做体验和发布。
