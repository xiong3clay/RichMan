三、变异 1：去掉 released 守卫、让 releaseIfUnclaimed 连续 release 两次
修改位置（副本 apps/server/src/ws.ts，仓库同位置 ws.ts:516-521）：
  原实现：
    let released = false;
    const releaseIfUnclaimed = (): void => {
      if (released) return;
      released = true;
      security.guard.release(ip, false);
    };
  变异后：
    let released = false;
    const releaseIfUnclaimed = (): void => {
      security.guard.release(ip, false);
      security.guard.release(ip, false);
    };
运行：
  cd D:\Lianjunjie\biancheng\richman-09a-fourthprobe
  corepack pnpm -s vitest run apps/server/tests/security.test.ts
实际结果（MUTATION1_EXIT=1）：
  × 49 握手失败只释放一次：基线连接 total 不变，60 次后 A 仍可 ready 517ms
  FAIL apps/server/tests/security.test.ts > 09A security > 49 握手失败只释放一次：基线连接 total 不变，60 次后 A 仍可 ready
  Error: 等待条件超时
   ❯ waitFor apps/server/tests/security.test.ts:57:50
   ❯ apps/server/tests/security.test.ts:681:5
  Test Files  1 failed (1)
  Tests  1 failed | 49 passed (50)

为什么变红：
  测试 49 先建立真实连接 A，等待 guard.total=1、perIp=1；再发一次缺
  Sec-WebSocket-Key 的升级请求，admit 使 total 临时到 2，close 应只释放这次
  无效握手，total 回到 1。没有 released 守卫时一次 close 释放两次，会把 A 的
  配额也扣掉，测试在 security.test.ts:681 等待 total 仍为 1 时超时。
  因此该变异证明测试 49 能抓住“双释放/漏守卫”，而不是只验证最终归零。

四、变异 2：把测试 50 反段的 autoPong:false 改成 true
修改位置（副本 apps/server/tests/security.test.ts:738；与仓库同文件同位置）：
  const closePeer = trackPeer(await Peer.open(closeServer.port, closeRoom, {}, { autoPong: false }));
  改为：
  const closePeer = trackPeer(await Peer.open(closeServer.port, closeRoom, {}, { autoPong: true }));
运行：
  corepack pnpm -s vitest run apps/server/tests/security.test.ts
实际结果（MUTATION2_EXIT=1）：
  × 50 心跳：autoPong 默认保活，autoPong:false 才超时关闭并释放 1831ms
  FAIL apps/server/tests/security.test.ts > 09A security > 50 心跳：autoPong 默认保活，autoPong:false 才超时关闭并释放
  Error: 连接未在时限内关闭
   ❯ Timeout._onTimeout apps/server/tests/security.test.ts:65:43
  Test Files  1 failed (1)
  Tests  1 failed | 49 passed (50)

为什么变红：
  反段依赖客户端不回 pong，服务端连续 missedPongs>=2 后在第三次 tick 关闭。
  把 autoPong 改回 true 后客户端自动回 pong，连接不会关闭，waitForClose 在
  1500ms 后抛“连接未在时限内关闭”。正段（默认 autoPong=true）仍为 OPEN、
  online=true、total=1；反段才应关闭、保留 offline 座位、total=0。
  该变异证明测试 50 不是只测“最终会断开”，而是真的区分了 autoPong 两种行为。

五、测试语义与 F18 文档
1) 测试 49（当前 security.test.ts:669-701）实际覆盖：
   - 建真实连接 A 并 join，guard.total=1、perIp=1；
   - 一次缺 Sec-WebSocket-Key 的升级返回 400；
   - 之后 total/perIp 仍为 1；
   - 再连续 60 次无效升级，仍为 1；
   - A 仍 OPEN，并能在 ready 后收到 room 消息；
   - 最后关闭 A，total 归零。
   结论：它证明无效握手只减自己那一次，基线连接的总数不被多减；不是 spy
   release 调用次数，而是用 total/perIp + A 可用性间接证明，足以抓住双释放。
2) 测试 50（当前 security.test.ts:703-758）实际覆盖：
   - 正段：默认 autoPong=true，3 次 tick，每次等 ping + 50ms；
     断言 OPEN、房间 online=true、guard.total=1；
   - 反段：autoPong:false，前两次 tick 也留 50ms，第三次 tick 后 waitForClose；
     断言连接关闭、房间座位保留但 online=false、guard.total=0。
   结论：正反两段真实区分 autoPong 行为；变异 2 已证明反段能变红。
