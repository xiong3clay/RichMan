============================================================

有问题：银行/私人账务内核的规则口径基本正确，但存在贷款 ID 可被覆盖、私人还款可绕过本轮利息、协议金额上限错误、HTTP 可被打崩四类会直接影响钱或服务的高危问题，另有交接基线与决策表失真，必须在本轮修掉；其余接口缺口可留到单元 03 之后。

二、必须现在修

【M1】packages/game-core/src/engine.ts:737（handleBorrowBank）；engine.ts:1188-1189（replaceBankLoan）；engine.ts:151-183（applyCommand）
问题：普通银行贷款 ID 直接使用客户端 commandId（`bank-${command.commandId}`）；引擎没有 commandId 去重表；replaceBankLoan 按 loanId 用 map 替换所有同名项。透支贷款 ID（engine.ts:481）反而是唯一的，说明只有 NORMAL 路径有该缺陷。
后果：两个客户端使用相同 commandId 时会产生两笔同 ID 贷款；之后 findLoan 只命中第一笔，而还款/结算会同时改写两笔，造成一笔贷款凭空消失或金额错乱。重放同一 commandId 还能二次放款（NORMAL 仅在该玩家仍有未结清贷款时被挡；首笔已 REPAID 或 OVERDRAFT 路径不受此限）。
建议修法：贷款 ID 改由引擎生成全局唯一值（如 `bank-${seatId}-${round}-${seq}`）；在状态或服务端增加 commandId→(载荷哈希, 原 outcome) 去重；写入 bankLoans 前断言 ID 全局唯一，重复直接报错而不是覆盖。
为什么会影响单元 03：单元 03 已加入 BETTING/TAX 与重连/重发场景，客户端重试是常态；ID 覆盖会同时破坏对账、存档与事件回放，且单元 04 的存档迁移无法修复已错账。

【M2】packages/game-core/src/private-loans.ts:346-378（repayPrivateLoan）；private-loans.ts:385-402（collectPrivateDebt）
问题：私人还款/催收都缺少 `currentRound < issuedRound` 的 INVALID_ROUND，也都缺少 `currentRound > lastInterestRound` 的 INTEREST_NOT_ACCRUED；银行侧两者都有（bank.ts:188-196）。accruePrivateInterest 又会跳过非 ACTIVE 合同（private-loans.ts:328-330），还款在金额归零时直接把状态置 REPAID（private-loans.ts:373）。
后果：在本轮利息尚未计入时全额还款，合同变 REPAID 后本轮利息永久不再计算，等于凭空少还一轮利息；在过期轮次调用还款也会被放行。催收虽不改状态，但会在本轮利息未计的情况下按旧余额计算可收上限。当前正常 ACTION 流程因 INTEREST 阶段先于 ACTION 而不易触发，但这是内核契约漏洞，任何新调用点（单元 03 的 TAX 自救、重放、坏存档恢复）都会直接踩中。
建议修法：照银行侧补两道校验：`currentRound < issuedRound → INVALID_ROUND`，`currentRound > lastInterestRound → INTEREST_NOT_ACCRUED`；repay 与 collect 都加，并补测试证明“未计息不可还/不可催、计息后可操作”。
为什么会影响单元 03：engine.ts:976-1009（repayPrivateCore）与 engine.ts:1011 起（collectPrivateCore）直接调用这两个函数；单元 03 的税收自救（TAX 阶段）新增了还款/催收入口，调用点变多，漏洞面随之扩大。

【M3】packages/shared/src/protocol.ts:7-11（moneyDigits / MoneyStringSchema）；protocol.ts:29-34（SliceBetPayloadSchema）
问题：`moneyDigits = "0|[1-9][0-9]{0,12}"` 允许 13 位任意值，`1000000000001`～`9999999999999` 以及负向超限值都能通过；没有对绝对值做 MAX_MONEY_CENTS 校验。
后果：协议入口放行超过 R01 规定上限（10^12 分）的金额；任何直接信任该 schema 的命令/下注路径都会把非法金额带进引擎。SliceBetPayloadSchema 已经引用该 schema，单元 03 接协议时必然使用。
建议修法：保留正则后追加 `refine(Math.abs(Number(s)) <= MAX_MONEY_CENTS)`，继续拒绝 `-0`；补边界测试：`"1000000000000"` 通过，`"1000000000001"` 与 `"-1000000000001"` 拒绝。
为什么会影响单元 03：单元 03/04 会把共享 schema 作为客户端命令的唯一入口；schema 错了，后面的引擎校验只能兜底，无法保证“协议层已拒绝非法金额”。

【M4】apps/server/src/http.ts:44-48（serveStatic 的 URL 解析与路径包含）；http.ts:52（fs.readFile）
问题：`new URL`/`decodeURIComponent` 没有 try；含 NUL 的路径会进入 `fs.readFile`；路径包含使用 `filePath.startsWith(path.resolve(staticDir))`。
后果（已用 node 复现）：`decodeURIComponent('%zz')` 抛 URIError；含 NUL 的路径 `fs.readFile` 同步抛 ERR_INVALID_ARG_VALUE；`D:\app\web2\x` 对 `D:\app\web` 的 startsWith 为 true。前两者在请求回调中未捕获，会让 Node 进程直接退出（LAN 上任何人可打崩服务）；后者可读到兄弟目录。
建议修法：URL 解析/decode 整段 try/catch，失败返回 400；拒绝含 `\0` 的 pathname；路径包含改用 `path.relative(base, target)`，要求结果不以 `..` 开头且不是绝对路径。
为什么会影响单元 03：单元 03 起服务端要真正暴露到局域网给手机访问，静态页与 /health 同进程；一次畸形请求就会让整局房间进程消失。

【M5】packages/shared/src/types.ts:87-91（CommandContext）；packages/game-core/src/engine.ts:1214（readPlayerId）及各 handler
问题：CommandContext 只有 nowMs/drawResult，没有 actorId；引擎所有操作者身份都从 `payload.playerId` 读取。
后果：服务端如果按现有接口原样转发客户端载荷，任何连接都能冒充他人借款、还款、催收、同意/拒绝请求；引擎自身的 currentSeat/lender 校验只能防“非本人当轮”，防不了“同轮冒名”。
建议修法：CommandContext 增加 `actorId`（由连接身份注入），引擎统一用 ctx.actorId 鉴权；payload.playerId 仅用于回显或一致性校验（不一致直接 UNAUTHORIZED）。
为什么会影响单元 03：下一步就是 socket/身份接入；接口不先定死，服务端只能继续从 payload 取身份，单元 04 再改会波及所有 handler 和测试。

【M6】packages/game-core/src/engine.ts:747（handleBorrowBank 的 `player.cents += amountCents`）
问题：借入后直接加余额，没有 MAX_MONEY_CENTS 校验；私人 accept 路径有入账上限校验（private-loans.ts 批准流程内），银行借款没有。
后果：余额可以越过 10^12 分上限；随后 views 汇总、快照编码或 assertCentsRange 会抛 RULE_INVARIANT（engine.ts:167-171 回滚）或把房间置 ERROR_PAUSED，玩家卡在无法继续提交的状态。
建议修法：抽一个统一入账 helper，入账前 `assertCentsRange(next)`，越界抛 INVALID_AMOUNT；借款、私人收款、下注派彩、催收入账全部走它。
为什么会影响单元 03：BETTING 派彩与 OVERDRAFT 会在同一次提交里多次加钱，散落的 `+=` 越多，越容易出现某条路径漏校验。

【M7】handoff/项目当前状态.txt:15、:19；handoff/单元02-成果报告.txt:7、:22、:41；handoff/单元02-下一阶段交接.txt:35；handoff/规则决策表.txt:1-4、:57
问题：项目当前状态仍写“规则引擎尚未接通”“6 文件/97 测试”；成果报告第 7/22 行写 private 34 条、全仓 91 条，第 41 行又写 97；下一阶段交接第 35 行写 91 条；工作区实际已是 11 文件/123 条（见第五节），且单元 03 代码尚未提交。决策表仍是占位版本，R06“待填”，没有按 AGENTS.md 单元 00 的要求给出逐条来源/原因/测试。
后果：下一单元会拿错误基线验收；R06 没有正式口径，正好覆盖本次发现问题的私人计息/还款/催收；成果报告的“已修”结论与代码不一致（例如曾声称 accrueInterest 对逾期抛 LOAN_OVERDUE、settleDue 只接受等于 dueRound，实际分别是静默钳制 bank.ts:159-177 和超时直接 DEFAULTED bank.ts:220-226，需在报告中更正）。
建议修法：复跑后统一三处数字并注明“工作区含未提交单元 03”；先提交或明确隔离单元 03 改动；补齐决策表 R06 与逐条来源/原因/测试行；把上述两条不实结论改成“实际行为 + 对应测试”。
为什么会影响单元 03：单元 03 已在进行中，交接说不清哪些是已提交、哪些是 WIP，验收与回退都会失控；R06 缺失会让私人账务继续按“实现即规则”漂移。

【D1】packages/game-core/src/engine.ts:413-427（runInterest）
问题：只比较 remainingCents 判断是否变化，漏掉仅 lastInterestRound 变化的情况。
后果：0 息或利率舍入为 0 时状态已变却返回 false、不发 INTEREST_ACCRUED，依赖该事件的推进逻辑会误判。
建议修法：同时比较 lastInterestRound/status，任一变化即算 changed。
为什么可以延后：当前阶段推进不依赖该事件，但单元 03 之后的事件回放/存档会依赖。

【D2】packages/game-core/src/engine.ts:268-272（BANK_DUE 到期贷款窗口）
问题：每笔到期贷款固定等待 bankDueSec，即使借款人余额明显不足或已离线。
后果：全房被一个无法 REPAY 的玩家拖满计时，破坏 R10 节奏。
建议修法：余额不足时直接按 insufficient_funds 结算，或允许超时/房主跳过。
为什么可以延后：规则允许倒计时兜底，先保证不卡死；体验问题可在联机阶段处理。

【D3】packages/game-core/src/engine.ts:151-183（applyCommand 返回值）；packages/shared/src/types.ts:93-98（TransitionResult）
问题：失败命令期间若 runSystem 推进了阶段，state/version 已变化，但 outcome 仍是 ok:false，TransitionResult 没有 stateChanged/committed 标记。
后果：服务端若按 ok:false 丢弃返回 state，会丢掉阶段推进；若广播又可能与客户端认知不一致。
建议修法：返回值增加 committed/stateChanged，服务端据此决定广播、落库与去重记录。
为什么可以延后：目前只有单元 03/04 的 socket 层会消费该字段。

【D4】packages/game-core/src/engine.ts:66、:782-793、:882（pendingRequestId 单槽）
问题：全局只有一个 pendingRequestId，等待答复期间 TAX/ACTION 都被锁住。
后果：与 D6“出借人可同时收到多个请求并逐一处理”不完全一致；多人局存在堵点。
建议修法：借款人仍限一个 PENDING，出借人侧改为收件箱列表，逐一处理不占用借款人轮次。
为什么可以延后：当前顺序回合下请求会即时结束，不会立刻出错，但扩到 D6 语义前必须改。

【D5】packages/game-core/src/private-loans.ts:38-50（LoanRequest）；private-loans.ts:224-247（acceptLoanRequest）；engine.ts:866-884（createPrivateRequest）
问题：请求结构没有 createdPhase/phaseInstanceId，也没有借款人私人债务/冻结应收快照；accept 不刷新 D5 风险快照。
后果：从发起请求到同意之间借款人若刚失信，出借人看到的仍是旧信用/旧失信欠款，D5“必须看到失信提示”会被绕过。
建议修法：补字段并在 accept 时重取信用与失信欠款；变化时提示或按 INVALID_REQUEST 拒绝。
为什么可以延后：当前违约只发生在 BANK_DUE，时间窗口小；但属于 R05/D5 的明确口径，单元 03 接 UI 前要定。

【D6】packages/game-core/src/bank.ts:159-177、:251-258；packages/game-core/src/private-loans.ts:491-499
问题：loan/request 对象本身没有结构校验，汇总函数只校验总和；负 remainingCents、乱写 status 可直接进入计算。
后果：坏存档会算出错误金额或抛错；accrueInterest 在 lastInterestRound < issuedRound 时还会补算放款前的轮次。
建议修法：入口增加 assertLoan/assertRequest（status 枚举、remaining 范围、lastInterestRound 与 issued/due 关系）；汇总前逐笔校验。
为什么可以延后：正常流程不会产生坏对象，属于存档/迁移防御，单元 04 前补即可。

【D7】packages/game-core/src/bank.ts:242-249；packages/game-core/src/private-loans.ts:481-489；packages/game-core/src/views.ts:128-129
问题：totalDebtCents/defaultedBankDebtCents/frozenCents/badDebtCents 只支持全局；views 把全局 FROZEN/BAD_DEBT 塞进个人视图。
后果：玩家同时是借款人和出借人时，冻结/坏账的角色混算，财务面板金额误导。
建议修法：汇总函数接受 playerId/role 过滤，视图分别展示“我欠的”和“别人欠我的”。
为什么可以延后：不影响主账，只影响展示与对账。

【D8】packages/shared/src/types.ts:100-109（PlayerView）；packages/game-core/src/views.ts
问题：视图没有 phaseInstanceId，而引擎已按 command.phaseInstanceId 拒绝过期命令（engine.ts:1268）。
后果：客户端拿不到该字段，无法回传 expectedPhaseInstanceId，过期计时器/过期命令防护形同虚设。
建议修法：在 PlayerView/RichPlayerView 补 phaseInstanceId（以及待处理请求的最小字段，不含第三人隐私）。
为什么可以延后：单元 03 目前仍可只在服务端校验，但联机前端接入前必须补。

【D9】packages/shared/src/types.ts:42-43（status 与 alive 并存）
问题：两个字段表达相近状态，破产/危险切换时可能漂移。
后果：R09“失信不淘汰”依赖 alive，而 UI/规则又可能读 status，迟早不一致。
建议修法：保留单一真相，另一个改为派生字段。
为什么可以延后：当前 engine 同步更新两者，尚未出现实际漂移。

【D10】packages/game-core/src/engine.ts:904、:908-912、:967-973（accept/closeRequestWindow）
问题：accept 只按 requestId 找 PENDING，不校验它就是 s.pendingRequestId；重放已处理请求返回 REQUEST_EXPIRED，而不是首次结果。
后果：一旦 D6 队列允许多个 PENDING，可能接受非当前窗口的请求并错误结束当前座位；重试拿不到幂等结果。
建议修法：accept 前校验 `requestId === s.pendingRequestId`；配合 M1 的去重表返回原 outcome。
为什么可以延后：当前单槽设计下不会并发多个 PENDING，先记录风险。

【D11】packages/game-core/src/private-loans.ts:346-352（repayPrivateLoan 的 currentRound == issuedRound）
问题：借出当轮允许原额还款；银行侧也允许，但方案没有明确私人侧是否应允许。未核实。
后果：若规则希望“借出当轮不能还款/不能刷请求”，当前实现会放行。
建议修法：先向用户确认；若不允许，补 `currentRound <= issuedRound → INVALID_ROUND`。
为什么可以延后：不影响金额守恒，属于规则口径待确认项。
