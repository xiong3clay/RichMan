M1（必须修）GAME_OVER / paused / !canSubmit 下销毁确认卡不渲染
====================================================================
现象：GameView.tsx 的 stage 渲染顺序是 paused → gameOver → !canSubmit → currentConfirmation，
所以顶部或 GAME_OVER 卡里的「销毁房间」点击后只 setConfirmAction，确认卡永远不出现。
规格要求：任何房间状态都能发起销毁。

改法：
1) 把 currentConfirmation !== null ? renderConfirm(currentConfirmation) 提到 paused / gameOver /
   !canSubmit 之前。即 stage 内先判断确认卡，再判断阶段卡。
2) 该顺序对现有告警/确认也成立（confirmations.ts 的 confirmationIsCurrent 已保证过期确认返回 null），
   不会让旧确认卡盖住新阶段。
3) 确认卡在 !canSubmit 时仍可打开；点「确认销毁」时若本地未连接，必须给出明确提示（见 S1），
   不能静默关闭。
4) 补测试（U8 扩展）：
   - phase=GAME_OVER、hostId=p1：房主看到「销毁房间」，点击后出现「销毁房间及数据？」与「返回」；
     点返回后确认卡消失、onDestroyRoom 未被调用；
   - paused=true 同上；
   - 非房主在 GAME_OVER 下看不到入口。
   GAME_OVER 下 DOM 里可能有两个入口，测试用更精确的选择器或取第一个/最后一个并写清。

S1（必须修）销毁请求本地发送失败时静默
====================================================================
现状：GameView.tsx:458-465 与 LobbyView.tsx:93-99 调 onDestroyRoom 但不看返回值；
App.tsx:272/276 的 onDestroyRoom={() => { clientRef.current?.destroyRoom(); }} 把 boolean 丢掉。
改法：
1) 把 onDestroyRoom 的签名改成 () => boolean（必填或可选都行，但调用方必须处理 false）。
   App.tsx 两处改为 onDestroyRoom={() => clientRef.current?.destroyRoom() ?? false}。
2) GameView 确认按钮：关闭确认后若返回 false，调用现有 setNotice("连接未就绪，销毁请求未发送")
   （或等价文案），不能静默。
3) LobbyView 增加一个本地 destroyError: string | null，false 时在按钮下方显示
   「连接未就绪，销毁请求未发送」；成功后清空。
4) 补测试：onDestroyRoom 返回 false 时确认卡关闭且有可见提示；返回 true 时无错误提示。

S2（必须修）collectLimits 数组含 null/非对象时抛 TypeError
====================================================================
位置：apps/web/src/game/steps.ts:65-73
现状：limits.find((entry) => entry.loanId === loanId) 对 null 元素直接抛错。
改法：用类型守卫，例如
  const found = limits.find(
    (entry): entry is { loanId: string; maxCents: string } =>
      entry !== null && typeof entry === "object" &&
      typeof (entry as { loanId?: unknown }).loanId === "string" &&
      (entry as { loanId: string }).loanId === loanId,
  );
保持：外层非数组 → null；找到但 maxCents 非字符串或非规范非负 → null；旧快照缺字段 → null。
补测试：collectLimits 为 [null]、[42]、[{loanId:1}]、[{loanId:"x", maxCents:null}] 时返回 null 且不抛；
数组里有合法元素时仍能正常返回。

S4（必须修）已加入的客户端收到 ROOM_NOT_FOUND 不回首页
====================================================================
规格 C.3.1 写明「房间已不存在时返回 ROOM_NOT_FOUND，客户端照常回首页」。
位置：apps/web/src/net/client.ts:399-413 的 error 分支。
改法：
1) 在 error 分支中，当 code === "ROOM_NOT_FOUND" && this.joined 时：
   - 与 room_destroyed 相同的清理（disposed=true、joined=false、session=null、clearSession()、
     清 retryTimer、关 socket）；
   - 调用 this.handlers.onRoomDestroyed?.({ roomCode: this.roomCode ?? "", byPlayerId: "" })；
   - 不再调用 onServerError（避免重复提示），直接 return。
2) App.tsx 的 onRoomDestroyed 文案按 byPlayerId 区分：
   byPlayerId 非空 →「房主已销毁房间，所有数据已删除」；
   byPlayerId 为空 →「房间已不存在或已被销毁，已回到首页」。
3) 未 joined 的 ROOM_NOT_FOUND 保持现有 abandonSession + onServerError 行为不变。
4) 补测试：joined 客户端收到 ROOM_NOT_FOUND → onRoomDestroyed 调用一次、onServerError 未调用、
   hasJoined=false、session 已清；未 joined 时仍走原路径。
5) 说明：正常销毁走 room_destroyed 广播；ROOM_NOT_FOUND 是“通知丢失/重连后发现房间没了”的兜底，
   不是替换 room_destroyed。

S5（必须修）ws 销毁只处理 current 连接，且单个 send 异常会中断后续关闭
====================================================================
位置：apps/server/src/ws.ts:248-261
改法：
1) 收集条件改为“该房间仍打开的所有连接”，不要求 current：
   peer.identity !== null && peer.identity.roomCode === roomCode && peer.ws.readyState === OPEN
   （用现有 ws 常量/枚举，不要魔法数字）。
2) 每个 peer 用 try/finally：try { send(room_destroyed) } catch { 记日志/忽略 }
   finally { detach(peer); peer.ws.close(4002, "ROOM_DESTROYED"); }
   任一 send 抛错不能阻断后续 peer 关闭。
3) 补测试：
   - 同房间存在一个非 current 但仍 open 的连接（例如被新 epoch 顶替的旧连接），destroy 后它必须收到
     room_destroyed 或被 4002 关闭；
   - 让一个 peer 的 send 抛错（可用 fake ws），其余 peer 仍被关闭。
   现有 D1/D3/D4 必须继续通过。
