三、必须修复 M1：PID 复用会误杀无关进程
位置：
  scripts/richman-common.ps1:110-131 Get-ProcessInfo
  scripts/stop.ps1:36-48 取到进程后直接 Stop-Process
代码事实：
  Get-ProcessInfo 只做两件事：
    1) Get-Process -Id <state.pid> 是否存活；
    2) ProcessName 是否等于 node（server）或 cloudflared（tunnel）。
  state 里虽然写了 startedAtUtc，但 Get-ProcessInfo 完全没有读取它，
  也没有比较进程启动时间、命令行或端口归属。
  white-list 只能区分“进程类型”，不能区分“是不是这次启动的那个进程”。

复现步骤：
  1) 在临时目录启动一个与 RichMan 无关的 node 进程（probe-sleep.js，PID 44404）；
  2) 在临时 dataDir 的 run/server.json 写入：
       {"pid":44404,"startedAtUtc":"2020-01-01T00:00:00Z","port":19999,...}
     实际该 node 进程的 StartTime 是：
       ACTUAL_START=2026-11-07T13:10:36Z
  3) 执行：
       powershell -ExecutionPolicy Bypass -File scripts/stop.ps1 -DataDir <临时目录>
实际结果：
  已停止 server（pid 44404）。
  已全部停止。
  {"ok":true,"stopped":[{"kind":"server","pid":44404,"running":false}],"warnings":[],"dataDir":"..."}
  DUMMY_ALIVE=false
  即：状态文件里的 startedAtUtc 与真实进程启动时间相差 6 年，stop 仍然杀了它。
  另一轮用 PID 48196 复现同样结果。

为什么是必须修复：
  - 规格第 50-51 行明确把“进程名白名单”当作“防 PID 复用误杀”，实现没有达到这个目标；
  - Windows PID 会复用；dataDir 里的 server.json/tunnel.json 会跨重启保留。
    重启后另一个 node 应用/cloudflared 拿到旧 PID 时，stop 会把它当成本服务杀掉；
  - 这不是“按端口杀陌生进程”，但仍然是“按过期 PID 杀陌生进程”，
    与“绝不杀无关进程”的安全目标冲突；
  - start-lan 的 alreadyRunning 判断和 status 的 processRunning 也复用同一个
    Get-ProcessInfo，会产生同样的误判（只是那两处不杀进程）。

建议修复：
  - 在 Get-ProcessInfo 中比较 state.startedAtUtc 与 $process.StartTime（允许 1-2 秒
    误差；跨时区统一用 UTC），不一致返回 $null 并让调用方 WARN；
  - 或者保存并比较命令行/可执行文件路径（server 必须含
    `--import tsx` 与 `apps/server/src/http.ts`；tunnel 必须是 cloudflared 路径）；
  - 不匹配时不要 Stop-Process，也不要静默删除状态；打印“状态文件与进程不匹配，
    可能 PID 已复用，未杀进程，请人工检查”，并保留状态文件供排查；
  - 修复后 M1 的测试：起一个无关 node，写同 PID 但旧 startedAtUtc 的状态，
    stop 必须不杀它。

四、必须修复 M2：start-tunnel 没有 -DataDir，且静默忽略
位置：
  scripts/start-tunnel.ps1:1-6 参数只有 -Port、-Cloudflared、-TimeoutSec、-CheckOnly；
  scripts/start-tunnel.ps1:14 $dataPath = Resolve-DataDir ''
  （start-lan.ps1、stop.ps1、status.ps1 都有 -DataDir）
代码事实：
  start-tunnel.ps1 没有 [CmdletBinding()]，是简单脚本；在 Windows PowerShell 5.1 下，
  未知命名参数会进入 $args 而不是报错。因此 `start-tunnel.ps1 -DataDir X` 不会提示
  参数不存在，而是完全忽略 X，继续按 RICHMAN_DATA_DIR 或默认 apps/server/data 解析。
  实测 CheckOnly 没有参数错误，输出照常。

复现 1（-DataDir 被忽略）：
  在 tunnelB/run/tunnel.json 放一个真实存活的假 cloudflared 状态
  （pid 28984，url=https://probe.trycloudflare.com）；
  执行：
    powershell -File scripts/start-tunnel.ps1 -CheckOnly -Port 18775 -DataDir tunnelA
  实际：
    {"ok":false,"reason":"LOCAL_SERVER_DOWN",...,"alreadyRunning":{"ok":true,"running":false,"url":""}}
  它没有看到 tunnelB 的状态，说明 -DataDir tunnelA 被忽略，读的是默认/环境目录。
  再执行：
    RICHMAN_DATA_DIR=tunnelB powershell -File scripts/start-tunnel.ps1 -CheckOnly -Port 18775
  实际：
    {"ok":false,"reason":"ALREADY_RUNNING",...,"alreadyRunning":{"ok":false,"running":true,"url":"https://probe.trycloudflare.com"}}
  只有环境变量能生效，-DataDir 不能。

复现 2（stop 漏停隧道）：
  powershell -File scripts/stop.ps1 -DataDir tunnelA
  实际：
    未在运行（没有找到 server.json / tunnel.json）。
    {"ok":true,"stopped":[],"warnings":[],"dataDir":"...tunnelA"}  exit 0
  powershell -File scripts/stop.ps1 -DataDir tunnelB
  实际：
    已停止 tunnel（pid 28984）。
    {"ok":true,"stopped":[{"kind":"tunnel","pid":28984,"running":false}],...}  exit 0
  即 stop -DataDir tunnelA 时隧道进程仍然活着；换到它真正写入的目录才停掉。

真实使用后果：
  1) 用户按 handoff/单元09B-运行与验收.txt:108 的“换端口/数据目录：加 -Port 8001、
     -DataDir D:\richman-data”执行：
       start-lan -DataDir X
       start-tunnel -DataDir X
     但 tunnel 状态和日志实际写到默认 apps/server/data/run/tunnel.json、logs/tunnel-*；
  2) 随后 stop -DataDir X 只看到 server.json，停掉本地服务，却把 cloudflared 和
     公网隧道留在运行状态；用户以为“全停”，公网入口仍然存在；
  3) 反过来不带 -DataDir 的 stop 会停隧道但看不到 X 里的 server，也会漏停。
  这不只是文档问题，是一键停止的安全/一致性问题。

规格冲突说明：
  09B 规格第 15 行说数据目录“可被 -DataDir / RICHMAN_DATA_DIR 覆盖”；
  第 88 行 start-tunnel 的参数表却没有 -DataDir。实现选择了第 88 行，但没有防呆，
  导致第 15 行、README:43-44、运行与验收:108 的承诺失效。
  无论最终选“给 start-tunnel 加 -DataDir”还是“明确只支持环境变量”，都必须：
    - 未知 -DataDir 不能静默忽略（至少报错并提示改用 RICHMAN_DATA_DIR）；
    - stop/status/start-lan/start-tunnel 的目录解析规则写成同一套；
    - 文档只保留与实现一致的说法。

建议修复：
  - start-tunnel.ps1 增加 [string]$DataDir = ''，改为 Resolve-DataDir $DataDir；
  - 五个入口脚本加 [CmdletBinding()]，让未知参数直接报错；
  - README、09B 运行与验收、注意事项同步“所有脚本都支持 -DataDir”；
  - 增加测试：start-lan/start-tunnel/stop 使用同一个临时 dataDir，stop 必须停掉
    两个状态文件（start-tunnel 可用假 cloudflared 进程，避免真实公网）。

五、应该修复 S1：健康检查只认 HTTP 状态，不认 RichMan 身份
位置：
  scripts/richman-common.ps1:74-89 Wait-HttpHealth 只判断 2xx/3xx；
  scripts/start-lan.ps1:55-62 用它判断已有 server.json 是否 ALREADY_RUNNING；
  scripts/status.ps1:27-30 只要 body 能解析成 JSON 就置 serverOk=true，
  不校验 body.service / body.ok。
事实：
  服务端 /health 的响应明确带 service:"richman"（apps/server/src/http.ts:214-218），
  但脚本没有使用这个身份字段。

复现：
  1) 在 18774 启动一个普通 node HTTP 服务，/health 返回 200 + {"hello":"world"}；
  2) 在临时 dataDir 写 server.json，pid 指向该 node，port=18774；
  3) start-lan -CheckOnly -Port 18773 -DataDir <临时目录>：
       {"ok":false,"reason":"ALREADY_RUNNING",...,
        "alreadyRunning":{"ok":false,"running":true}}
       exit 1
  4) status -Port 18774 -DataDir <临时目录> -Json：
       {"ok":true,...,"server":{"ok":true,"port":18774,"rooms":0,"connections":0,"reason":""},
        "tunnel":{...}}
       exit 0
  用 text/plain 200 时 start-lan 仍判 ALREADY_RUNNING；status 会因 JSON 解析失败而报错，
  但 start-lan 的误判与 body 类型无关。

为什么应该修复：
  - 同端口有别的 HTTP 服务、或状态文件过期的 PID 恰好指向另一个 node 时，
    start-lan 会拒绝启动并说“已在运行”，status 会把陌生服务报成 RichMan 健康；
  - 与 M1 叠加时，stop 还可能杀错 node；
  - 修复成本低：Wait-HttpHealth 解析 JSON，要求 ok===true 且 service==='richman'；
    status 同样要求；隧道 URL 的 /health 也是同一个服务，可复用同一判断。

六、应该修复 S2：Write-RunState 失败后子进程残留、无状态
位置：
  scripts/start-lan.ps1:141-163 Start-Process → Wait-HttpHealth → Write-RunState；
  scripts/start-tunnel.ps1:95-116 同样的“先起进程、后写状态”结构；
  scripts/richman-common.ps1:37-51 Write-RunState。

复现（start-lan）：
  1) 临时 dataDir 下把 `run` 建成普通文件而不是目录；
  2) 执行 start-lan -Port 18778 -DataDir <临时目录> -TimeoutSec 10；
  3) 健康检查通过后，Write-RunState 写 run\server.json.tmp 抛异常：
       使用“3”个参数调用“WriteAllText”时发生异常:
       “未能找到路径 ...\run\server.json.tmp 的一部分。”
       位置 richman-common.ps1:46
  4) 脚本 FAIL_EXIT=1、没有 server.json，但 netstat 显示：
       0.0.0.0:18778 LISTENING 24268
     Get-CimInstance 确认命令行是：
       node.exe --import tsx --no-warnings apps/server/src/http.ts
     即启动成功的服务器还在监听，stop 因为没有状态文件而找不到它。
     复核时只杀了这个自己启动的 24268，未动其他 node。

对照（健康检查失败路径是好的）：
  start-lan -Port 18777 -TimeoutSec 0：
    FAIL_EXIT=1
    服务启动失败（健康检查超时），进程已停止。日志：...
    没有 server.json，18777 无 LISTENING。
  说明“让健康检查立即超时”的失败路径会清理子进程且不写状态；
  S2 专指“健康检查已通过、随后写状态失败”的路径，规格/文档没有覆盖。

为什么应该修复：
  - 磁盘满、目录权限变化、run 被同名文件占用等都可能让 Write-RunState 抛错；
  - 结果是一个仍在 0.0.0.0 监听的服务器，没有状态文件，stop 无法发现；
  - start-tunnel 同一结构失败时，会留下 cloudflared 和公网隧道（按代码路径；
    本次未实跑该分支，避免再开公网隧道做破坏性写失败）。

建议修复：
  - 用 try/catch 包住 Start-Process 之后的全部步骤；任何异常都 Stop-Process
    刚启动的子进程（核对 StartTime/命令行），删除 .tmp 和半写状态，打印日志后
    以非 0 退出；
  - start-tunnel 同理，异常时停止 cloudflared；
  - 增加“run 是文件”或“状态目录不可写”的测试。

七、应该修复 S3：状态文件坏 JSON 时 stop 静默当作“未在运行”
位置：
  scripts/richman-common.ps1:25-35 Read-RunState，JSON 解析失败返回 $null；
  scripts/stop.ps1:30-39 把 $null 当成“没有状态文件”。

复现：
  1) 启动一个无关 node（PID 42380）；
  2) 写 badjson/run/server.json 内容 `{not valid json`；
  3) stop -DataDir badjson：
       未在运行（没有找到 server.json / tunnel.json）。
       {"ok":true,"stopped":[],"warnings":[],"dataDir":"..."}  exit 0
  4) 实际 DUMMY_ALIVE=true，坏状态文件仍在。
为什么应该修复：
  - 原子写降低了坏文件概率，但磁盘异常/手工编辑仍可能发生；
  - 当服务实际在跑而状态文件坏了时，stop 打印“未在运行”并 exit 0，用户会误以为
    已停止；不要求它按端口杀进程，但至少应该 WARN 并返回非 0，提示人工检查。
建议：
  - stop 先 Test-Path；文件存在但 Read-RunState 返回 null 时，WARN
    “状态文件存在但无法解析，未按端口杀进程，请人工检查”并 exit 2/3；
  - status 同样显示“状态文件损坏”，而不是当作没有隧道/服务。

八、测试充分性（单独结论）

    e) run 为文件/状态写失败 → 子进程被清理。
  测试仍用 Windows-only、随机端口、临时目录，避免 8000 和 apps/server/data。
