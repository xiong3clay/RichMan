二、must-fix
------------------------------------------------------------
M1. 编码 /api 路径回退到 index.html（HTTP 404 规格失败）
文件/行：
- apps/server/src/http.ts:193-198（计算 decodedPath）
- http.ts:207、:221、:225、:231（路由仍用 url.pathname）
- http.ts:239（静态用 decodedPath）；http.ts:165-174（SPA fallback）
现象：
  /api/unknown       -> 404 application/json {"ok":false,"error":"NOT_FOUND"}
  /api%2Funknown     -> 200 text/html <!doctype html>（index.html）
  /api%2Frooms       -> 200 text/html（index.html）
  /api%2funknown     -> 200 text/html
原因是路由判断看未解码的 url.pathname：`/api%2F...` 不以 `/api/` 开头，
落到 serveStatic(decodedPath)，而 decodedPath 没有扩展名时触发 SPA fallback。
规格 09A-服务加固与限流.txt:99-100 要求未知 /api/* 返回 404 JSON 且不得
回退 index.html；这是明确的 must-fix（不是只影响静态页面：它会把 API
命名空间伪装成 SPA 200）。
复现（本次实跑）：
  node --import tsx - <<'NODE'
  import { startServer } from './apps/server/src/http.ts';
  const s = await startServer({ host: '127.0.0.1', port: 0 });
  for (const p of ['/api/unknown','/api%2Funknown','/api%2Frooms']) {
    const r = await fetch(`http://127.0.0.1:${s.port}${p}`);
    console.log(p, r.status, r.headers.get('content-type'));
  }
  await s.close();
  NODE
建议修法：
- 所有路由/前缀判断统一用 decodedPath（health、/api/rooms、/api/*），
  `if (decodedPath.startsWith("/api/")) sendJson(404 NOT_FOUND)`；
- 保留 decodedPath 给 serveStatic；增加编码路径测试（至少 /api%2Funknown）。

M2. init 在 conn 创建阶段抛错时 guard 配额泄漏
文件/行：
- apps/server/src/ws.ts:419-425：Connection 对象的 `createdAt: now()`
  在 `try` 之前；`try` 从 :425 才开始。
- ws.ts:506-511：onUpgrade 在调用 init 前就 `initialized = true`；
  因此 init 在 :425 前抛错时，外层 catch 看到 initialized=true 不再 release。
- ws.ts:444-451 的 catch 只覆盖 try 内的监听注册。
现象（独立探针，仓库外副本）：
  用 `startSecurityServer({}, { now: () => { throw new Error("clock"); } })`
  打开一个 /ws；连接失败后
  `s.security.guard.stats()` 为 `{total:1, ...}`，预期是 total=0。
这直接违反 F1“init 抛错也必须恰好释放一次”；同一个 IP 可因重复失败
最终耗尽 maxConnections/未认证额度。
建议修法：
- 把 `const conn = {... createdAt: now() ...}` 也放进 try；或先在 try 外
  不读 now（createdAt 在 try 内赋值），catch 中 release(false)、
  connections.delete/destroy；
- 或者 initialized 只在 init 成功返回后置 true，并确保 init 内部异常
  不会双重 release；增加 `now` 抛错的回归测试。

三、should-fix
------------------------------------------------------------
S1. TokenBucket 只增不减，prune/size 无运行时调用
文件/行：
- apps/server/src/security.ts:78-112（tryTake 创建 Map 项；prune/size）
- security.ts:271-282（六个桶实例）
- security.ts:103-112 的 prune 只被 security.test.ts:97 直接调用；
  grep `prune(`/`.size()` 无 startServer/ws/http 运行时调用点。
现象/风险：
- createRoomBucket/joinBucket/resumeBucket 以 IP 为 key；
  resumeRoomBucket 以房间码为 key；commandBucket/economicBucket 以
  房间码|玩家|type 为 key。房间销毁、IP 变化后 key 永不删除；
  唯一 IP/历史房间码/旧玩家组合会持续累积。
- 交接注意事项:19 写“暂不构成泄漏；地图大小受活跃 key 数约束”，但代码没有
  任何 prune 定时器，实际是“历史唯一 key 数”而非“活跃 key 数”；该结论未验证。
建议：
- 在 startServer/security runtime 加一个 unref 的周期 prune（如 5 分钟，
  idle 10 分钟），close 时清理；或 tryTake 在 size 超阈值时惰性 prune；
- 用注入 now 测 runtime 下旧 key 被清、活跃 key 不受影响；
- 更新交接，不要写“暂不构成泄漏”除非有容量/增长数据。

S2. 满房 join 跳过 joinBucket，存在限流绕过/刷接口风险
文件/行：apps/server/src/ws.ts:267-274
  - 先计算 roomFull；`if (!roomFull && !security.joinBucket.tryTake(conn.ip))`
    才计 bucket；roomFull=true 时不消耗任何 join 额度，随后 transact/
    sessions.join 返回 ROOM_FULL。
复核探针（仓库外，joinBurst=1、joinPerMinute=0，房间先填满 10 人）：
  对第三个新连接连续发送 3 次 join，收到
  `["ROOM_FULL","ROOM_FULL","ROOM_FULL"]`，没有一次 RATE_LIMITED。
影响：
- join 限流可被用于反复刷满房请求；全局 per-connection 60/s、连接总/单 IP
  上限仍在，因此不是权限/状态绕过，但会造成 CPU/房间队列压力；
- rooms.test 第 11 人 ROOM_FULL 旧契约与此直接相关（rooms.test.ts:71）。
建议：
- 增加独立的 fullJoinBucket（或带保留 ROOM_FULL 的专用计数），满房请求
  也消耗；首次/前 burst 仍返回 ROOM_FULL 以维持旧测试，超过后 RATE_LIMITED；
- 或在满房分支仍 tryTake 一个专用的满房桶，不把结果提前返回；
- 补满房连续 join 测试，断言最终 RATE_LIMITED；保留 rooms.test 契约。
