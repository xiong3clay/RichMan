F6（must，M1）路由统一使用 decodedPath
----------------------------------------------------------------
文件：apps/server/src/http.ts:193-240。

现状：路由用未解码的 url.pathname（:207 /health、:221 POST /api/rooms、
:225 GET /api/rooms、:231 /api/ 前缀），而 serveStatic 用 decodedPath(:239)，
导致 /api%2Funknown、/api%2Frooms、/api%2funknown 落到 SPA 回退 200 index.html。

修法：
1) /health、/api/rooms、/api/ 前缀三处判断全部改用 decodedPath。
2) 增加 decodedPath === "/api" → JSON 404（与 N1 一并处理）。
3) 保持 POST/GET 方法与判定顺序不变；serveStatic 继续用 decodedPath。
4) 编码路径不得再触发 index.html 回退。

必测（38 起编号从 38 顺延，见 F11 汇总）：GET /api%2Funknown、/api%2Frooms、
/api%2funknown 均 404 且 content-type application/json；GET /api 也 404 JSON。

F7（must，M2）init 创建 Connection 阶段也必须恰好释放一次
----------------------------------------------------------------
文件：apps/server/src/ws.ts:419-453（init）、:491-513（onUpgrade）。

现状：`const conn = { ... createdAt: now(), rateStart: now() ... }` 在 try 之外，
try 从 ws.on("message") 才开始；onUpgrade 在调用 init 前已置 initialized=true，
因此 conn 创建阶段抛错时外层 catch 不再 release，guard.total 泄漏。

修法（推荐，禁止双重释放）：
- init 内先声明 `let conn: Connection | null = null;`，把 Connection 对象创建、
  connections.set、四个 ws.on 全部放进 try。
- catch 中：
  * conn !== null：若 !conn.released 则置 released=true 并
    `security.guard.release(conn.ip, conn.authenticated)`，connections.delete(ws)；
  * conn === null：`security.guard.release(ip, false)`；
  * 再 try { ws.terminate(); } catch {}，最后 throw error。
- onUpgrade 的 initialized 语义保持不变：handleUpgrade 同步失败且 callback 未执行时
  外层 catch release；callback 已执行时由 init 自己负责且只释放一次。
- 不得改动 markAuthenticated 的时机（bind 时仍只一次）。

必测（39）：注入 now 第一次调用抛错（之后返回 Date.now），打开 /ws → 连接失败后
`s.security.guard.stats().total` 必须为 0；再开一条正常连接仍能加入。
测试要等待 stats 归零（waitFor），并避免定时器未处理异常。

F8（should，S1）TokenBucket 惰性 prune，禁止无限增长
----------------------------------------------------------------
文件：apps/server/src/security.ts:78-113。

修法：
- 增加常量（模块内）：PRUNE_AT_SIZE = 1024、PRUNE_IDLE_MS = 10 * 60_000。
- TokenBucket.tryTake 开头：`if (this.buckets.size >= PRUNE_AT_SIZE) this.prune(PRUNE_IDLE_MS);`
  （在创建/取用当前 key 之前执行）。
- 保留公开的 prune(idleMs) 与 size()，供测试与后续维护使用。

必测（38 之外的编号由 Trae 顺延，最终编号在 F11 表内统一）：
- 构造 1024 个 key（now=t0），now 前进 11 分钟后 tryTake 一个新 key →
  size() 必须为 1（旧的都被清掉）；
- 同一 now 下先建 1023 个旧 key，再建活跃 key "hot"，然后 tryTake("new") →
  size() 为 2，"hot" 仍在（活跃 key 不被清）。

F9（should，S2）满房 join 也必须限流，同时保留 ROOM_FULL 旧契约
----------------------------------------------------------------
文件：apps/server/src/security.ts（SecurityRuntime/SecurityOverrides）、
apps/server/src/ws.ts:264-280。

修法：
1) SecurityRuntime 与 SecurityOverrides 增加 fullJoinBucket；
   createSecurityRuntime 缺省创建 `new TokenBucket(limits.joinBurst, limits.joinPerMinute / 60_000, now)`。
2) ws.ts join 分支改为：
   - 计算 roomFull（现有逻辑）；
   - `const joinBucket = roomFull ? security.fullJoinBucket : security.joinBucket;`
   - `if (!joinBucket.tryTake(conn.ip)) { sendError(RATE_LIMITED); return; }`
   - 删除当前“满房跳过桶”的分支。
3) 语义：前 joinBurst 次满房请求仍走 sessions.join 返回 ROOM_FULL；之后返回 RATE_LIMITED。
   rooms.test.ts:554-561 的“第十一人 ROOM_FULL”必须继续通过（它只发 1 次）。

必测：服务 joinBurst=10、joinPerMinute=0；先用 10 个连接正常 join 填满房间，
第 11 个连接连续发 11 次 join → 前 10 次 ROOM_FULL，第 11 次 RATE_LIMITED。
