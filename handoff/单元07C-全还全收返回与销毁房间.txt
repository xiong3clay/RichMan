1. 需求 A：全部还款 / 全部催收
====================================================================
1.1 语义
- 「全部还款」= 把当前选中那一笔债务的剩余应还金额一次还清（不是“还清所有贷款”）。适用于 repayBank 与 repayPrivate。
- 「全部催收」= 把当前选中那一笔私人合同的剩余应收金额一次收清。适用于 collectPrivate。
- 两者都是“把金额输入框填成剩余全额”，不自动提交；玩家仍需点「确认还款 / 确认催收」。理由：一次点击就转走全部金币不可逆，保留一次确认。
- 只有金额恰好等于剩余全额才算“全部”；填 968 以外的数字仍是部分还款，走原逻辑。

1.2 可用性（灰色不可选）
- 全部还款可用条件：本人当前金币 >= 该笔 remainingCents；否则按钮 disabled，并在按钮附近显示原因，例如
  「金币 500 分不足 968 分，不能一次还清」。
  金币为负（危险状态）时同样不可用。
- 全部催收可用条件：对方当前可被收走的金额 >= 该笔 remainingCents；否则 disabled，提示
  「对方当前仅有 300 分，无法一次收清」。
- 金额比较全部用十进制整数字符串做，不转浮点；沿用 apps/web/src/net/wire.ts 的规范与 formatCents 展示。

1.3 服务端必须提供“对方可收上限”
- 现状：WireSnapshotView.finance.privateLoans 只有 remainingCents，前端看不到借款人当前金币，无法判断“对方不足”。
- 在 packages/game-core/src/views.ts 的 PlayerFinanceView 增加：
    collectLimits: { loanId: string; maxCents: Cents }[]
  只包含：本人是出借人、合同 status === "ACTIVE" 的私人合同；
  maxCents = max(0, min(loan.remainingCents, 借款人当前 cents))。
  不含第三人的合同，不新增任何“对方金币”字段。
- 隐私说明写进代码注释：出借人本来就有权知道“这笔最多能收回多少”；当 maxCents < remaining 时等价于暴露借款人余额不足，这是催收必需信息，已由用户确认接受。
- apps/web/src/game/steps.ts 增加纯函数：
    collectLimitOf(view, loanId): string | null   // 字段缺失/非法返回 null
    canCollectAll(view, option): boolean | null   // null 表示旧快照无法判断，调用方回退“以服务端为准”并允许点击
  以及还款侧 canRepayAll(view, option): boolean（纯字符串比较）。
- apps/web/src/net/wire.ts 的 WireFinance 增加 collectLimits?: WireLenderLimit[]（沿用 {playerId, maxCents} 形状不合适，新增 {loanId, maxCents} 类型）。

1.4 UI 落点（两处都要，不能只改行动阶段）
- 行动 Q3 金额卡（GameView.tsx stage === "debtAmount"）：金额输入框下方、确认按钮上方，加一行快捷项按钮。
  文案：还款 → 「全部还款（968 分）」；催收 → 「全部催收（968 分）」。
  点击后 setAmount(remainingCents)，清掉旧 notice，不提交。
- 危险自救阶段的 collectAmount 卡：同样加「全部催收（968 分）」。
- 键盘/触屏：按钮至少 44px 高；金额输入框里的值被填充后玩家可继续改。
- 不要新增步骤、不要改 deriveStep 的优先级。

3. 需求 C：房主销毁房间及数据
====================================================================
3.1 产品定义
- 只有房主能发起；任何房间状态都可发起（大厅、对局中、暂停、结束），但必须二次确认：
  第一次点「销毁房间」，显示确认卡：
    「销毁房间及数据？」
    「房间内所有玩家会被移出，服务器上的存档将删除，无法恢复。」
    按钮：「确认销毁（不可恢复）」 + 「返回」。
- 销毁成功后：服务端删除内存房间 + 磁盘 rooms/<code>/ 目录（含 snapshot/bak/events/corrupt），断开该房间所有连接，广播一条 room_destroyed；所有客户端清 sessionStorage、停止重连、回大厅首页并显示
  「房主已销毁房间，所有数据已删除」。
- 非房主点击不可用；若服务端返回 NOT_HOST，前端提示“只有房主可以销毁房间”。
- 房间已不存在时返回 ROOM_NOT_FOUND，客户端照常回首页。

3.2 协议（packages/shared/src/protocol.ts）
- 新增客户端消息：{ type: "destroy_room" }（strict）。
- 新增服务端消息：{ type: "room_destroyed", roomCode: RoomCodeSchema, byPlayerId: string }（strict）。
- 加进 ClientLobbyMessageSchema / ServerLobbyMessageSchema；PROTOCOL_VERSION 不动。
- 注意：ClientLobbyMessageSchema 与 ClientGameCommandSchema 都是 safeParse，destroy_room 不含 gameId，必须落在 lobby 分支。

3.3 服务端
- rooms/manager.ts 新增：
    async destroyRoom(roomCode: string, playerId: string): Promise<void>
  步骤：resolvePlayer 确认成员身份 → hostId !== playerId 抛 LobbyError('NOT_HOST') →
  this.transact(roomCode, () => { this.rooms.delete(roomCode); })；
  transact 在 candidate 为 null 时会调 store.deleteRoom(code) 并清空 sessions 索引（已有逻辑，直接复用）。
  另外清 durablePending.delete(roomCode)。
  不要手工 rm -rf 目录；只会走 store.deleteRoom（file-store 用 tomb 目录保证原子）。
- rooms/scheduler.ts 增加 public cancelRoom(roomCode: string): void（内部就是现有 private cancel）；销毁后调用，防止残留 timer 再推进。
- ws.ts 的 handleLobby 增加分支：
    else if (message.type === "destroy_room") {
      // 先收集 peers，销毁后 current() 会因 sessions 清空而全部为 false
      const peers = [...connections.values()].filter(peer => current(peer) && peer.identity!.roomCode === identity.roomCode);
      await manager.destroyRoom(identity.roomCode, identity.playerId);
      scheduler.cancelRoom(identity.roomCode);
      for (const peer of peers) {
        send(peer, { type: "room_destroyed", roomCode, byPlayerId: identity.playerId });
        detach(peer);
        peer.ws.close(4002, "ROOM_DESTROYED");
      }
    }
  注意顺序：先收集 peers 再 destroy；broadcast 不需要参与。
  若 destroyRoom 抛错，handle 现有 catch 会把 LobbyError 转成 error 消息。
- server 测试（新增）：
  1) 房主 destroy → 空间删除（检查 data/rooms/<code> 不存在）、其他连接收到 room_destroyed、连接被关闭；
  2) 非房主 → NOT_HOST，房间仍在，数据仍在；
  3) destroy 后用原 roomCode join/resume → ROOM_NOT_FOUND；
  4) 对局中（PLAYING）destroy 也能删除且不触发 scheduler 继续；
  5) 重复 destroy → ROOM_NOT_FOUND（幂等失败，不崩）。
  测试可用临时 RICHMAN_DATA_DIR 与 fake timers。

3.4 Web
- net/client.ts：
  - ClientHandlers 增加 onRoomDestroyed(info: { roomCode: string; byPlayerId: string }): void。
  - 新增 destroyRoom(): boolean（仅 joined 时可发）。
  - handleRaw 增加 type === "room_destroyed"：停止重连（disposed = true）、clearSession()、joined=false，回 onRoomDestroyed。
  - 不要把 room_destroyed 当作普通 error；不要触发 REPLACED 分支。
- App.tsx：注册 onRoomDestroyed，重置 roomCode/room/joined/snapshot，设置入口横幅文案并清 session。
- LobbyView.tsx：props 增加 onDestroyRoom?: () => void；仅房主渲染「销毁房间」按钮（ghost/danger 风格），点击展开内联确认（确认 + 返回），确认后调用。
- GameView.tsx：GameViewProps 增加 onDestroyRoom?: () => void；房主可见入口：
  - 顶部房间信息区或 GAME_OVER 卡里「销毁房间」；
  - 点击后复用 renderConfirm 机制（新增 ConfirmAction kind: "destroyRoom"），确认卡含「返回」；
  - 确认时调用 client.destroyRoom()，失败按普通 error 展示。
  实现时优先复用现有 confirmAction 状态，不要新增全局模态框。
- 服务端不广播 room 快照给已销毁房间；客户端不要在收到 room_destroyed 后自行重连。

3.5 权限与隐私
- room_destroyed 只发给该房间当前连接；不发玩家列表之外的信息。
- 不删除其他房间目录；不清理无关历史。
