==============

复核对象：单元 05A「最小可玩联机 UI + 双客户端冒烟」
复核方式：只读审查。未改代码、未 commit；除本文件外未写任何文件。
基线：HEAD 946824b（工作区未提交改动即 05A 范围）；core 134 / server 80 / typecheck 0 / smoke:lan PASS。

一、结论
--------
有条件通过（必须先修 4 项，再进入 05B）。

05A 的主方向是对的：
  - 前端只消费服务端 view，没有在客户端算金币/利息/债务/杠杆，金额全程十进制字符串；
  - 单个客户端内 snapshot 按 version 过滤，不会回退；
  - resume 只用 sessionToken 且只走消息体，URL 只有房间码；
  - 断线退避、两个标签页互斥（REPLACED 停止重连）实现正确；
  - 非本人回合/错误阶段/破产/等待私人答复时按钮禁用且给出中文原因；
  - command_result 的失败会显示 code + message；
  - 大厅错误码映射完整；
  - 冒烟是真实 startServer + 真实 WebSocket，不是 mock，version 单调、借款 +2500、下注 ±100 且合计 0 的断言有效；
  - 作用域干净：game-core 未改，package.json 只加脚本、没有新增依赖。

但按「会算错钱 / 会卡死 / 会泄露 / 会让玩家误解」的标准，仍有 4 项必须现在修：
  1. 「退出房间」从不发送 leave，房主退出会让整间房无法开始；游戏中退出会清掉唯一 token，永久无法恢复。
  2. 自动重连后的 resume 失败没有收口：界面会停在旧对局、显示“已连接”，动作失败也没有提示。
  3. 服务端删掉“命令后补发 snapshot”后，被拒绝/版本冲突的命令不再回推最新本人快照，与 V1.3 第 292 行冲突。
  4. 游戏内服务端 error 没有渲染；同时本地金额上限比服务端宽，超大金额会让整条命令在协议层失败而界面完全无反馈。

修完这 4 项后，05A 可以算“代码验证通过”；但单元 05 要求的真实浏览器两人一局、刷新/断网恢复、另一设备核对、10 客户端自动化、真人试玩记录都还没有做，不能对外说单元 05 已完成。


二、必须现在修
--------------
【M1】退出房间不发送 leave，且无条件清会话
文件：
  apps/web/src/App.tsx:164-178（backToLobby）
  apps/web/src/App.tsx:249-253（footer「退出房间」）
  apps/web/src/App.tsx:34-35（startRoom 替换旧 client 时也不 leave）
服务端其实已经支持：
  apps/server/src/ws.ts:185（type === "leave" → detach + sessions.leave）
  apps/server/src/rooms/manager.ts:283-304（大厅离开删座位并转交房主）
  apps/server/src/rooms/session.ts:161-167（大厅离开删 token/恢复码；游戏中只标离线、保留 session）

问题：
  backToLobby 只做 dispose() + clearSession()，Web 端任何地方都没有发送 { type: "leave" }。
后果：
  - 大厅：离开者的座位和 ready 状态保留。若离开者是房主，hostId 仍指向已离线的房主，
    其他人永远收不到 NOT_HOST 以外的结果（只有房主能 start），2 人房里剩下的人直接卡死；
    房间要等所有人走光才会被删除。
  - 游戏中：服务端把 leave 当断线处理（保留座位），但客户端把唯一 token 清掉了，
    且 UI 没有恢复码入口，玩家再也回不到原座位；界面也没有任何“不可恢复”的警告。
  - 建房后立刻点退出、或加入过程中点退出，同样会留下幽灵座位。
建议：
  - backToLobby 在 dispose 之前，对仍处于 OPEN 的 socket 发送 { type: "leave" }。
    发送后设置一个 leaving/disposed 标志，忽略该连接后续的 error（避免误报“尚未加入房间”）。
  - 大厅阶段：发送 leave 后 clearSession（服务端会删 token）。
  - 游戏阶段：发送 leave 后不要 clearSession（服务端非 LOBBY 的 leave 不删 session），
    回到入口并提示“可输入房间码恢复原座位”；或至少弹确认框说明退出后本局无法恢复。
  - startRoom 替换旧 client 前也走同一个 leave 流程。
  - 补一个真实客户端测试：房主在大厅点退出 → 另一方收到 room 且 hostId 已转移；
    游戏中退出 → 原 token 仍可 resume。

【M2】自动重连后 resume 失败没有收口，界面永久停在旧对局
文件：
  apps/web/src/App.tsx:55-58（只有 onJoined 把 joinedRef 置 true）
  apps/web/src/App.tsx:72-88（onServerError 只在 !joinedRef.current 时才清理）
  apps/web/src/net/client.ts:181-191（重连 onopen 直接 resume，没有重置“已加入”状态）
  apps/web/src/net/client.ts:197-201（resume 失败时服务端不 close，客户端也没有重试）
  apps/web/src/App.tsx:192-193（GameView 不接收 lobbyError）

问题：
  首次 join/resume 成功后 joinedRef.current = true。之后 WebSocket 断开并自动重连时，
  startRoom 不会被再次调用，joinedRef 仍为 true。此时 resume 若失败
  （服务重启丢内存房间 → UNAUTHORIZED/ROOM_NOT_FOUND；恢复码在别处轮换 token → 旧 token 失效），
  onServerError 的 !joinedRef.current 分支不执行，客户端既不 dispose、也不清 session、也不回入口。
  服务端 sendError 后不会关闭连接（apps/server/src/ws.ts:51-53），所以客户端也不会再触发 onclose 重连。
后果：
  - 玩家停在旧 snapshot 的游戏页，页脚显示“已连接”，没有任何错误提示（GameView 不渲染 lobbyError）。
  - 点击借还/下注只会在服务端得到 NOT_JOINED/未认证类错误，界面表现为“点了没反应”。
  - 这是最容易让玩家误以为“对局还在继续”的卡死路径，也是 05 验收“断网恢复”必须覆盖的场景。
建议：
  - 在 onStatus("connecting") 或 onStatus("open") 时把 joinedRef.current 置 false，
    由随后的 joined 再置 true；这样 resume 失败会走现有清理分支。
  - 或让 RichmanClient 显式区分“resume 被拒”回调，App 收到后 clearSession + dispose + 回入口，
    并把错误显示在入口页。
  - 清理时保留/展示服务端 code+message；对 ROOM_NOT_FOUND/UNAUTHORIZED 可提示
    “房间已不存在（服务重启会丢内存房间）”。
  - 补测试：加入并开始 → 服务端丢失该房间 → 客户端重连 → resume 失败 →
    应回到入口且显示错误，而不是停在旧对局。

【M3】被拒绝/冲突的命令不再回推最新本人快照，违反 V1.3 第 292 行
文件：
  apps/server/src/ws.ts:200-204（05A 改为只发 command_result）
  apps/server/src/rooms/command-queue.ts:98-107（校验失败时 result 不变，不调用 commit）
对照：
  V1.3 第 292 行：“行动中的借款/还款/催债/结束行动：严格校验 expectedGameVersion；
  冲突返回最新本人快照，玩家重新确认后用新 commandId；不得自动按新余额重放旧经济意图。”
  旧代码在每条命令后都 snapshot(conn)；这次为了去重只保留了 commit 广播，
  成功路径没问题，但被拒绝/冲突路径没有任何 snapshot。
后果：
  - 服务端不再满足“冲突返回最新本人快照”的协议约定。
  - 当前 Web 客户端通常已经通过冲突提交的广播拿到了最新快照，所以短期不一定可见；
    但一旦客户端错过广播（或未来客户端严格按 292 实现），它会拿旧 expectedGameVersion
    反复重试，直到下一次别的玩家行动/阶段推进才有新快照。
  - 冒烟没有覆盖被拒命令，因此这条回归没有被测试发现。
建议：
  - 在执行命令前记录 state.version；execute 返回后，如果当前 state.version 与执行前相同
    （说明没有 commit，也就没有广播），再补一次 snapshot(conn)；有 commit 时保持现在的“不重复补发”。
  - 或在 command_result 里带最新本人 view（协议改动更大，不推荐 05A 做）。
  - 冒烟补一条：用过期 expectedGameVersion 发一条行动命令，断言 command_result 为
    VERSION_CONFLICT，并且随后收到 version 等于当前状态的新 snapshot。

【M4】游戏内服务端 error 不显示；本地金额上限宽于服务端，导致可触发的静默失败
文件：
  apps/web/src/net/wire.ts:167（isCanonicalCents 允许 15 位）
  packages/shared/src/protocol.ts:9-15（服务端只允许 13 位且 ≤ 10^12）
  packages/shared/src/protocol.ts:95-108（金额字段不合规 → 整条 ClientGameCommandSchema 解析失败）
  apps/server/src/ws.ts:207-208（解析失败走 sendError("INVALID_MESSAGE")，不是 command_result）
  apps/web/src/App.tsx:72-73（error 写入 lobbyError）
  apps/web/src/App.tsx:192-193（GameView 不接收该错误）
  apps/web/src/GameView.tsx:149-156（只渲染 command_result，不渲染服务端 error）

问题：
  - isCanonicalCents 的正则是 ^(0|[1-9][0-9]{0,14})$，最多 15 位；
    服务端是 13 位且绝对值 ≤ 1,000,000,000,000。
    例如输入 9999999999999（13 位但超过上限）或 10000000000000（14 位），
    本地校验通过，命令被发出；服务端在协议层判为 INVALID_MESSAGE，不会返回 command_result。
  - App 把这条 error 放进 lobbyError，但 GameView 没有这个 prop，游戏页完全看不到。
后果：
  - 玩家输入一个看起来合法的较大金额，点击后界面毫无反应（没有 notice、没有 banner），
    会误以为按钮坏了或操作已生效；在 BETTING 阶段同样可能静默丢掉一次下注。
  - RATE_LIMITED、NOT_JOINED、INVALID_MESSAGE 等游戏内服务端错误全都静默
    （REPLACED 有独立的“已在另一页面恢复”页，属例外）。
建议：
  - isCanonicalCents 与服务端完全对齐（直接 import MAX_MONEY_DIGITS / MAX_MONEY_CENTS，
    或 13 位 + 字符串比较上限），并在本地给出中文提示。
  - 把 lobbyError（或单独的 serverError）传给 GameView 并渲染；收到新 snapshot 或下一次操作时清理。
  - 大厅的 handleReady/handleStart 也检查 sendLobby 的 false 返回值，断线时给出“连接未就绪”。
  - 补测试：14 位/超 10^12 的输入被本地拦截；游戏内注入一个 error 消息时界面可见。


三、可延后（按目标单元分组）
----------------------------
05B（建议优先）：
  1. 倒计时到 0:00 后按钮仍可用（GameView.tsx:20-43、66-87）。服务端会先推进系统动作再校验，
     最终返回 VERSION_CONFLICT 并在 banner 显示，所以不会算错钱；但应在 remaining<=0 时
     加入中文原因“本阶段时间已到，等待服务端推进”，仍以服务端为准。
  2. 断线/离线时未禁用按钮（GameView 不接收连接状态）。当前点击会显示
     “连接未就绪或快照尚未到达，命令未发送”，不算静默；建议把 status 传入 GameView 统一禁用。
  3. 大厅 ready/start 的 sendLobby 失败没有反馈（App.tsx:154-162）。
  4. 被替换/已 dispose 的旧 client 仍可能把消息回调进 App（client.ts:193-195、218，
     handleRaw 不检查 disposed），在 StrictMode 双挂载或快速加入两个房间时可能造成
     snapshot 回退或误显示“已在另一页面恢复”。建议 handler 捕获 client 代次，或在 dispose 后忽略消息。
  5. onclose 没有检查 close code 4001（client.ts:197-201）；若 REPLACED 错误帧丢失，
     旧标签页会重连并把座位抢回来（会收敛，但违背“旧标签页不自动争抢”）。加 code===4001 兜底。
  6. 房主直接关页（不走 leave）后没有 30 秒转交（manager.ts:266-272）。
     V1.3 第 273 行用“可”，不是硬性；但两人房里房主关页会让剩下的人无法 start，建议 05B 补。
  7. schemaVersion 直接复用存档的 SNAPSHOT_SCHEMA_VERSION（ws.ts:111、game-core engine.ts:53），
     冒烟又硬断言 ===1（scripts/smoke-two-clients.ts:275）。单元 06 一旦因存档字段升版，
     冒烟会假失败。建议区分 wire/view schema version，或至少断言 typeof number。
  8. 未确认命令 ID 不持久化/不重发（client.ts:149-164 每次生成新 commandId）。
     V1.3 第 298 行要求断线时保存未确认 ID；当前若 BORROW_BANK 的成功应答丢失，
     玩家再点一次会用新 ID 再借一笔。当前快照通常会显示借款结果，所以不是高频问题，
     但属于账务风险，建议 05B/07 补 pending command 列表并按原 ID 原载荷重发。
  9. 恢复码没有 UI（client.ts:228-245 收到后丢弃，只存 sessionToken）。
     刷新当前标签页可以恢复（sessionStorage），但关标签页/换设备无法用恢复码找回；
     单元 04 的服务端已支持 recoveryCode。建议 07 做恢复码展示/输入，或在 05B 明确写“未实现”。

07：
  1. 私人借款请求/同意/拒绝/催收/还私人、BANK_DUE 决策、危险自救、完整债务中心
     （GameView 只有银行借还/结束行动/下注；05 规格明确这些走默认超时，07 做完整 UI）。
  2. 游戏中看不到他人“离线”（PublicPlayerView 没有 online，views.ts:23-34；V1.3 第 303/378 行要求）。
     当前断线玩家的回合只会默默超时，其他玩家不知道在等谁。
  3. 可收回应收/冻结/坏账分项、私人合同明细、历史与信用详情未展示（07 债务中心）。
  4. DEFAULTED 玩家仍可点“借银行”和“杠杆 2 倍”，只靠服务端 CREDIT_DEFAULTED/规则拒绝；
     失败会显示 code+message，不算静默，但 07 应前置禁用并说明原因。
  5. 客户端完全忽略 events 消息（client.ts 只处理 joined/room/started/snapshot/
     command_result/error）；事件流、税收/危险提示等要到 07/08 才有，当前不影响账务。

08：
  1. 倒计时用客户端 Date.now() 与 deadlineAt 直接相减（GameView.tsx:29-35），
     未用 serverNow；客户端时钟偏差会让显示的剩余时间不准（服务端仍按自己的时间推进）。
  2. “操作成功（状态版本 N）” 永不自动清除，也不标注是哪条命令（GameView.tsx:149-156），
     下一轮仍可能看到旧的“成功”。
  3. 入口页初始 status 为 closed，页脚显示“连接断开，自动重连中”，但此时根本没有连接；
     建房失败只显示 HTTP 状态，不展示服务端返回的错误体（App.tsx:118-126）。
  4. 手机触控、横竖屏、无障碍、确认弹窗、美术/音频均未做（单元 08）。


四、测试缺口
------------
1. 没有浏览器 e2e：package.json:18 的 test:e2e 仍是“尚未实现”，
   方案单元 05 指定的 tests/e2e/lan-smoke.spec.ts 不存在；当前 smoke 只驱动裸 WebSocket，
   完全没有覆盖 App/RichmanClient/GameView 的渲染、按钮禁用、snapshot 过滤、重连和退出。
2. 没有真实浏览器两人一局、刷新恢复、短断网恢复、另一设备/手机加入的记录；
   也没有 10 个自动化客户端验证排队与下注（单元 05 验收项）。
3. 冒烟的 seat 断言依赖跨连接到达顺序（scripts/smoke-two-clients.ts:178-182）：
   a.send(join) 后立刻 b.send(join)，再断言 a=seat1、b=seat2；两个 TCP 连接的到达顺序并无保证，
   存在偶发失败风险。建议先 await a 的 joined，再发 b 的 join。
4. 冒烟没有覆盖：被拒命令/版本冲突后的 snapshot（M3）、resume/replaced、leave/房主转移、
   非当前玩家代操作、同 commandId 重发与换载荷、金额上限、隐私（b 看不到 a 的贷款/下注金额）、
   command_result.gameVersion 与 snapshot.version 的一致性、phaseInstanceId 跨轮变化、
   计时器超时推进、schemaVersion>1。
5. 没有 Web 端单元测试：isCanonicalCents/formatCents、acceptSnapshot 的
   “小于当前 version 丢弃、等于接受”、App 的 joinedRef 生命周期、Countdown，均无断言。
6. 没有 M1/M2/M4 的回归测试（退出 leave、resume 失败回入口、游戏内 error 可见）。
7. 现有 server 80 条测试覆盖了队列/会话/计时器，但没有断言“被拒命令后客户端收到最新快照”，
   所以 M3 没有被现有测试拦住。
