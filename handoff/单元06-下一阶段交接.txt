一、入口与数据流
http.ts CLI → FileRoomStore(dataDir) → rooms/recovery.ts loadAllRooms → RoomManager.restoreRoom → HTTP listen/WS。
生产CLI数据默认apps/server/data，RICHMAN_DATA_DIR覆盖；嵌入startServer需显式传dataDir或store。
HTTP POST建房await createRoomPersisted；GET /api/rooms公开最少房间元数据；health计数含恢复房间。
join/resume/ready/start/rematch/leave → 原房间队列 → manager.transact → 候选完整快照 → commit → 发布事件/绑定。
游戏命令 → GameCommandProcessor → applyCommand → commitTransition(state+hash+reply+events) →
writeSnapshotAtomic → audit append/fsync → 内存/缓存 → player view + 过滤事件 → scheduler。
旧规则引擎仍只处理纯状态；没有加入socket、时钟读取或磁盘访问。
失败路径：旧内存+paused+ERROR_PAUSED；rename后已提交内容用durablePending对齐后才能有下一次写入。
关闭服务先停止scheduler/心跳/接入，终止WS，再queue.drain，保证测试/嵌入关闭不遗留磁盘任务。

二、接口
shared协议新消息：{type:"resume_game"}；错误码ERROR_PAUSED；房间与snapshot view包含paused。
resume_game要求当前已认证房主、PLAYING、paused；否则NOT_HOST/INVALID_STATE。
成功先保存paused=false与续时后的state和GAME_RESUMED事件，再广播room/snapshot/events并schedule。
resumeFromPause(state,{nowMs})：GAME_OVER同引用；其余同phase重建时限/实例，version/eventSeq+1。
ACTION/TAX有PENDING私人请求时同时续request与窗口；TAX自救dangerDeadline续时；不动账本/赌注/行动记录。
GAME_RESUMED是公开事件type，payload:{code:"GAME_RESUMED"}；EngineState无events数组，服务端构造并保存事件。
RoomStore：commitRoom(code,snapshot,events)、deleteRoom(code)；FileRoomStore还提供loadAll与测试故障选项。
AtomicOptions.failAt为before_rename/after_rename；checkpoint只供受控测试精确等待kill屏障，正常不配置。
SnapshotSessionStore同步读写manager候选态，必须由外层await manager.transact才算身份提交。
CommandProcessor生产WS固定atomicCommit:true；当次record作为commit第三参数，与state同rename，不预缓存成功。
manager.reconcileDurable返回是否应用了pending；WS对齐前捕获有效owner，对齐后撤销已失效身份，避免座位复用越权。
